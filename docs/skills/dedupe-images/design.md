# dedupe-images 设计说明

维护 [`skills/dedupe-images`](../../../skills/dedupe-images/SKILL.md) 前先读本文。记录目标、判定规则和关键决策，只写代码与 git 历史看不出的意图。

## 目标与边界

对图片库做按目录的去重：用户给出一个总目录，skill 递归遍历其中的每个目录（含总目录本身），在每个目录内找出“同名带副本标记、内容相同”的重复图片，按固定规则保留一张，其余移入回收站；带副本标记而原名空缺的文件改回原名。同一批图片以两种文件名各存一份、名字对不上的，按命名对应另行识别（见“跨名称匹配”）。

分工：脚本有把握的部分（计划中的移走与改名）由模型抽查后直接执行；拿不准、需要理解命名与目录结构才能取舍的，脚本整理成案例和判断材料，模型给出建议，用户确认后由脚本校验执行（见“案例”）。无论哪条路径，被移走的文件都必须在保留处有 SHA-256 相同的文件，模型判断失误最多留错名字或结构，不丢图片。

- 文件级去重以目录为处理单元，只比较目录自己直接包含的图片；跨目录同名同内容的单个文件不视为重复。
- 目录级去重另行比较整个目录：一个目录的图片全部在另一个目录里（按哈希）时，整目录移走（见“目录级重复”）。
- 不区分“底层目录”和中间目录：既有图片又有子目录的目录同样处理其中的图片。
- 不做相似图片识别（不同分辨率、不同压缩、不同文件名的同一张图），只处理下载、复制、同步时产生的命名副本。

## 判定规则

### 扫描范围

- 跳过以 `.` 开头的子目录和文件：总目录若是挂载点，其下会有 `.Trash-<uid>`；外置盘上的 macOS 会生成 `._<name>` AppleDouble 文件和 `.DS_Store`。
- 跳过符号链接，无论指向子目录还是文件；不跟随目录链接，也就不会陷入循环。
- 跳过软件目录：目录里直接有 `exe` `dll` `so` `dylib` `msi` `assets` `pak` 文件，或目录名以 `.app` 结尾，就连同全部子目录不处理，并在计划里列出。总目录本身不按此跳过（plan 与 clean 一致），根目录下零星一个 `exe` 不应让整个库被跳过。
- 只处理扩展名在图片清单内的普通文件，扩展名不区分大小写。

### 图片扩展名

`jpg` `jpeg` `jpe` `jfif` `png` `gif` `webp` `bmp` `tif` `tiff` `heic` `heif` `avif` `jxl` `svg` `dng` `cr2` `cr3` `nef` `arw` `raf` `orf` `rw2`

分组时同一格式的别名视为同一扩展名：`jpg` `jpeg` `jpe` `jfif` 归一，`tif` `tiff` 归一，`heic` `heif` 归一。

### 副本标记

把文件名拆成 `<主名><副本标记…>.<扩展名>`。下表的标记可以叠加（`a (1) (1).jpg`、`a - 副本 - 副本.jpg`），从外向内反复剥离直到剥不动，剩下的是主名。每层标记带一个序号，未写数字的记为 1。

**强标记**：命名本身就说明它是副本，总是参与分组。

| 形式 | 来源 | 序号 |
| --- | --- | --- |
| `a (1).jpg` | Chrome、Edge、Firefox 下载，Windows 资源管理器重名，Google Drive，Telegram | 括号内数字 |
| `a(1).jpg` | Android、部分国产软件 | 括号内数字 |
| `a（1）.jpg`、`a （1）.jpg` | 全角括号 | 括号内数字 |
| `a - Copy.jpg`、`a - Copy (2).jpg` | Windows 资源管理器在同目录粘贴 | 1；括号内数字 |
| `a - 副本.jpg`、`a - 副本 (2).jpg` | 中文 Windows | 同上 |
| `Copy of a.jpg`、`Copy (2) of a.jpg` | Windows XP | 1；括号内数字 |
| `复件 a.jpg`、`复件 (2) a.jpg` | 中文 Windows XP | 1；括号内数字 |
| `a copy.jpg`、`a copy 2.jpg` | macOS Finder 复制 | 1；空格后数字 |
| `a 副本.jpg`、`a 副本 2.jpg` | 中文 macOS Finder | 同上 |
| `a (copy).jpg`、`a (another copy).jpg`、`a (3rd copy).jpg`、`a (Copy 2).jpg` | GNOME Files | 1；another 为 2；序数或数字 |
| `a (副本).jpg`、`a (另一个副本).jpg`、`a (第 3 个副本).jpg` | 中文 GNOME Files | 同上 |
| `a_copy.jpg`、`a-copy.jpg`、`a_副本.jpg` | 手工或脚本复制 | 1 |
| `a (conflicted copy 2026-01-01).jpg`、`a (某人's conflicted copy …).jpg` | Dropbox 冲突副本 | 1 |
| `a.jpg.1`、`a.jpg.2` | wget 重名 | 末尾数字；剥离后扩展名取前一段 |

英文单词不区分大小写，空格可为一个或多个。

**弱标记**：同样的写法也常见于正常文件名（`IMG_0001.jpg`、`2026-01-01.jpg`、`photo 2.jpg`），只有当同一子目录里存在剥离后的主名文件时才视为副本。

| 形式 | 来源 | 序号 |
| --- | --- | --- |
| `a-1.jpg` | Safari 下载 | 末尾数字 |
| `a_1.jpg` | 部分下载器、脚本 | 末尾数字 |
| `a 2.jpg` | macOS Finder“保留两者” | 末尾数字 |

### 分组与确认

1. **名称组**：主名与归一后的扩展名都相同的文件归为一组。主名先做 Unicode NFC 归一（macOS 来源的文件名常是 NFD），再按 casefold 忽略大小写。
2. **体积**（用户的条件二）：名称组内按字节数细分，体积相同且至少两个文件的才进入下一步。截断的图片体积不同，在这一步就被排除。
3. **哈希**：对进入这一步的文件算 SHA-256，哈希相同的文件构成一个重复组。
4. **损坏判定**：体积相同但哈希不同时，对 jpg、png、webp、gif、heic、avif、jxl 这些压缩格式逐个检查损坏特征：含 4 KiB 对齐的全 0 块，或 JPEG/PNG 去掉末尾 0 字节后缺结束标记（`FFD9`、`IEND`）。恰好只有一种内容完好、其余都有损坏特征时，保留完好的一份，损坏的全部移入回收站（计划中标 `damaged`）。否则再逐字节比较：若其余每种内容都与某一种内容只在若干位置不同、且这些位置在它们那里全是 0，它们是那一份被局部清零后的副本，同样移走、保留那一份（那一份自身缺结束标记也保留，它不比副本差）。仍判不出、或是未压缩格式时不删，整理为文件案例交模型判断。

一个名称组可能拆出多个重复组，也可能一个都没有。例如 `a.jpg` 100B、`a (1).jpg` 100B、`a (2).jpg` 200B：只有前两个是重复组，`a (2).jpg` 不动。

### 页码序列

漫画、图集常把页码写成 `page (1).jpg…page (95).jpg`，与浏览器下载副本的 `(n)` 同形，整个序列会落进同一个名称组。名称组内带序号文件的最内层序号有 4 个及以上不同取值时，视为页码序列：最内层序号是页码，更外层的标记才是副本标记（`page (5) (1).jpg` 是第 5 页的副本）。序列内：

1. **同一页码内照常去重**：`page (5).jpg` 与 `page (5) (1).jpg`、`page (1).png` 与 `page (001).png` 按体积、哈希与损坏判定处理，同体积不同内容同样按损坏与清零规则处理，判不出的成为文件案例。保留顺序为副本层少的优先，再优先补零书写，然后按文件名长度与字典序。
2. **不同页码的同内容文件只在整套重复时移走**：序列里同时有补零（`page (001)`，最内层序号以 0 开头且不止一位）和不补零两套编号，且补零一套至少 90% 的文件在不补零一套里有同内容文件时，判定为同一作品存了两套编号（常见为编号错开一位），移走不补零一套中与补零一套同内容的文件，保留补零一套。随之消解的同页码冲突（两套编号错开后，同页码两份自然内容不同）不再列入人工确认。
3. **其余情况不动**：单一编号格式内相邻或相隔的同内容页（重复的插页、过场页），以及两套编号只零星几页相同（两个不同版本恰有几页一样），都视为作品本身的页面，不删除，也不进人工确认。
4. **不改名**：原名由剥离全部标记得到，序列里会变成 `page.jpg`，因此序列内的文件一律不改名。

### 跨名称匹配

名称组和页码规则处理完后，再对整个目录找“同一批图片以两种文件名各存一份”的重复。三种对应依次匹配，都要求体积与 SHA-256 相同，不做损坏判定、不产生人工确认项、不改名；前一步的保留项和待删项不参与后一步的配对。计划组以 `match` 标明来源（名称组规则为 `name`）。

1. **只差补零**（`zero_pad`）：所有数字去掉前导 0 后名字相同，如 `0630_A_76.png` 与 `630_A_76.png`。保留文件名更长（补零）的一份。不要求整套：作品本身不会用两种补零写法排同一页。
2. **只差开头流水号**（`index_prefix`）：去掉开头的 `数字_`（或空格、`-`）后名字相同，剩余部分须含字母，如 `001_hellven_000.jpg` 与 `121_hellven_000.jpg`。保留流水号小的。须整套：待删数至少占目录图片数的 25%；零星几对多是合并章节时每章重复的声明页，删掉会让后面的章节缺页，不动。
3. **两套命名模板整套对应**（`name_set`）：把数字替换为 `#` 得到命名模板（`01.jpg` 属 `#`，`page (001).jpg` 属 `page (#)`，`6 (1).jpg` 属 `# (#)`），同一模板的文件为一套。两套都至少 10 个文件、文件数之比不低于 0.9，且一套至少 90% 的文件在另一套里有同内容文件（前面规则已移走的文件算已覆盖）时，移走这一套里有对应的文件，没有对应的留下。保留优先不带副本标记的套，其次文件多的套。编号可以错开（`001.jpg` 对 `page - (2).jpg`，`1.jpg` 对 `6 (1).jpg`）。

页码序列里补零与不补零两套（`page (001)` 与 `page (1)`）同属一个模板，仍由页码规则处理；`page (100)` 起两种写法相同，这个漏判不变。

### 目录级重复

先于文件级去重执行，被移走的目录不再做目录内去重。比较总目录下（跳过的软件目录除外）任意两个目录，不限于兄弟目录；每个目录只看它直接包含的文件。

1. **包含关系**：目录 B 的每张图片（按 SHA-256）都能在目录 A 里找到，称 A 包含 B；两边图片内容集合相同为“内容相同”，否则为“子集”。要求 100% 包含，差一张都不算。先按体积求交集筛候选（B 的每个体积都要在 A 里出现），再算哈希。
2. **保留顺序**：图片多的目录优先；一样多时，所在父目录子目录多的优先（更完整的合集，使两个合集之间的取舍方向一致，不出现互相拆的情况），再优先目录名不带副本标记（`X (2)`、`X copy` 等强标记，序号小于 1000）的优先，再优先目录名更长的（`[Pisanto (皮三豆)] …` 优于 `[Pisanto] …`，带画廊号的优于不带的），最后按路径字典序。按这个顺序逐个决定：目录被某个已保留的目录包含时考虑移走，指向排序最靠前的那个保留目录；否则保留。这样链式包含（A ⊂ B ⊂ C）和多份副本都指向最终保留的目录，保留目录不会再被移走。
3. **自动移走**的条件同时满足：
   - B 的每个图片文件名在 A 里原样存在且内容相同：内容相同且同名，或同名子集且 B 覆盖 A 至少 90% 的内容（按去重后的哈希计，A 自身存了两份的不拉低比例），即同一份东西的不完整版；
   - B 没有任何子目录（含隐藏子目录）：整目录移走会连带子目录，而子目录可能正是别处的保留目录；
   - B 不含符号链接；
   - B 的每个非图片文件在 A 里都有同名同内容的文件，避免把只在副本里有的说明文件、未完成下载（`.!qB`）一起扔掉。隐藏文件（`.DS_Store` 等）不比较，随目录移走；
   - 不拆散合集：B 与 A 是兄弟目录，或 B 的父目录里其余子目录也都被移走（整个合集重复）。否则移走 B 会让它所在的合集缺一部分。降级后父目录多了留下的子目录，反复检查直到稳定。
4. **交模型判断**（计划 `dir_review`，带原因，并整理进 `cases`）：内容相同但文件名不同（留哪一边就是留哪套名字）、同名子集只占保留目录一部分（单话与合集、独立作品与杂图包）、文件名改过的子集（单章目录与合集、旧版与新版、整理好的单本与作者杂图包）、会拆散所在合集的，以及因含子目录、符号链接或非图片文件不一致而不能自动移走的包含关系。每项附图片数、文件名原样相同的数量和几对改名样例。

计划中每个被移走的目录记录保留目录、关系类型，以及每个文件的体积、哈希和在保留目录里对应的文件名（`keep_name`）。

### 案例

计划的 `cases` 把不自动处理的项整理成案例，编号 `c001` 起：

- **合集由单章拼成**：被同一保留目录包含的几个目录，去掉内容完全相同的重复单章后至少两个，图片数之和等于合集图片数且 SHA-256 多重集合一致时，与这个合集有关的包含关系合成一个案例，计划记 `composed`（`dir`、`chapters`、`duplicates`）。重复单章优先舍弃与其他单章不在同一父目录的。只认这样严格拼成的；单章有重叠、或只覆盖合集一部分的，仍按下面的规则分案例。
- **目录案例**：其余 `dir_review` 中被包含目录与保留目录在同一父目录下的，每对一个案例；不在同一父目录下的，按两边父目录这一对合成一个案例（`黄蓉襄阳后记/` 与另一个大合集之间的 63 对是一个案例），因为两个合集之间的取舍要整体决定。
- **文件案例**：同名同体积、内容不同且损坏判定与清零规则都判不出的文件。

`show <计划> [编号…]` 按需生成判断材料，不写进计划：每对包含关系的图片数与改名样例；涉及目录（不超过 3 对时逐个列出）的图片数与体积、命名模板及数量、首尾文件名样例、主模板编号范围与缺号、其他文件、子目录；同父目录的案例列出父目录的子目录，跨父目录的列出两个合集及各自没有对应关系的子目录；文件案例列出两份文件的完整路径、损坏特征、不同字节的个数与范围。路径首尾或某一级名字首尾带空白时用「」括起显示：真实库里 `黄蓉襄阳后记/` 下的章节目录名为 ` 01` 这样带前导空格，混在缩进里看不出，子 agent 照抄成 `01` 后整个案例因路径不存在被跳过。`show <计划> --sample N` 给出自动部分的抽查样本：目录级每种关系、文件级每种匹配方式（`name`、`zero_pad`、`index_prefix`、`name_set`、损坏副本、只改名）各均匀取 N 个，并列出文件级移走超过一半图片的目录。

模型的决定写成决策文件（`root` 与 `actions`），操作有四种：`trash_matching`（`path` 为目录，把它直接包含的非隐藏文件中、SHA-256 在 `keep` 路径下出现过的展开为逐个文件的 `trash`，`keep` 不变；一个都没有时整案跳过）；`move`（把 `src` 移进已存在的目录 `dest`，可选 `name` 作为移入后的文件名，同一案例内与目标里都不能有同名项，不能移进将被移走的路径）、`trash`（`path` 为目录或文件，`keep` 为保留路径列表）、`keep`（不动，仅记录）。`trash_matching` 在校验前展开，`keep` 按执行前的路径计算，所以可以是本案例里将被移动的单章。`apply-decisions` 按案例分组，每个案例先校验全部操作：路径须在总目录内；`trash` 路径下每个非隐藏文件（不含将被移出的 `move` 源）都要在 `keep` 路径下、或移进 `keep` 的 `move` 源里找到 SHA-256 相同的文件，比对时先按体积筛选再算哈希，且 `keep` 不能落在被移走的路径里；遇到符号链接拒绝。任何一项不满足，整个案例跳过、不做任何改动。通过后先移动、再移入回收站，最后删除移动源和被移走路径留下的空上级目录（放在最后，避免先把待移走的父目录删掉）。加 `--check` 只做校验，列出通过的案例将执行的操作与跳过的原因，不检查平台、不改动文件，有跳过项时退出码为 1；它按顺序模拟前面通过的案例，后面的案例用到前面将移走或移动的路径时报“与案例 X 冲突”，否则两个各自成立的案例（A 保留 B、B 保留 A）都会通过校验、执行时第二个才被跳过。真实执行时每个案例重新计算哈希，不沿用前面案例的缓存：前面的案例可能已把某个路径换成别的文件，旧哈希会让校验误以为保留处还有一份。合并两个合集时用它找出一方独有、需要先移过去的文件。

### 非图片杂项

`clean <总目录>` 在 plan 之前运行，按文件名识别固定几类非图片杂项，不加 `--apply` 只列出，加了才移入回收站并逐级删除因此变空的目录：未下载完的残缺文件（BitComet 的 `.bc!`、qBittorrent 的 `.!qB`）、广告链接与网页（`.url` `.torrent` `.mht` `.mhtml` `.html` `.htm`）、下载站与电子书元数据（`.opf` `.nfo` `ComicInfo.xml`）、文件夹图标（`desktop.ini` `.ico`；`.ico` 因此不在图片扩展名里）、看图软件与系统残留（文件名含 `thumbs` 的 `.db`，如 `复件 (1) Thumbs.db`、`Thumbs(1).db`；以 AppleDouble 魔数 `00 05 16 07` 开头的 `._*`；`.ehviewer` `.thumb`）。与 plan 不同，它不跳过隐藏文件（`._*`、`.ehviewer` 正是隐藏的），仍跳过隐藏目录（`.Trash-<uid>`）、符号链接和软件目录。残缺文件若没有去掉后缀的同名完成文件，单独列出，这些页移走后作品就缺了。其余非图片文件只按扩展名计数供汇报。

### 保留

每个重复组保留一张，其余移入回收站；经损坏判定的组只在完好的内容里选。按下列键排序取第一个：

1. 没有副本标记的优先（`000c01.jpg`）。
2. 标记层数少的优先（`a (1).jpg` 先于 `a (1) (1).jpg`）。
3. 逐层序号小的优先，按整数比较（`a (2).jpg` 先于 `a (10).jpg`）。
4. 文件名更短的优先，仍相同再按文件名字典序，保证结果确定。

### 改回原名

带副本标记的文件在以下条件同时满足时改名为原名，不论它是去重后的保留项（`a (1).jpg` 与 `a (2).jpg` 去重后只剩 `a (1).jpg`），还是本来就单独存在、没有重复的副本（目录里只有 `a (3).jpg`）：

- 去重后它所在的名称组只剩这一个文件。名称组里还有体积不同或判不出取舍的文件时，说不清谁该拿原名，不改。
- 各层序号都小于 1000：`Trip (2019).jpg` 这类括号里是年份的正常命名不改。
- 原名未被占用：目标路径不存在（失效的符号链接也算占用），或者占用它的正是本组要移走的损坏文件（`037.jpg` 损坏、`037 (1).jpg` 完好时，移走前者后后者改名为 `037.jpg`）。macOS 默认文件系统不区分大小写，存在性检查自然覆盖大小写不同的同名文件。
- 原名不以分隔符（`-`、`_`、`.`、`~`、`#`）结尾：`page - (1).jpg` 去掉序号只剩 `page -`，说明这个序号是页码。2026-11-22 自动部分执行后，`Elven Desires - Distress Signal 2` 的 `page - (n)` 一套被跨名称匹配移走，只剩没有对应的 `page - (1).jpg`，原规则会把它改成 `page -.jpg`。

原名由保留项剥离全部副本标记得到，主名保持它自身的写法，扩展名用它自己的扩展名（`A (1).JPEG` 改为 `A.JPEG`），wget 形式去掉末尾序号（`a.jpg.1` 改为 `a.jpg`）。

## 删除：移入回收站

脚本只依赖 Python 3.14+ 标准库，回收站按平台分别实现。

### Ubuntu：按 FreeDesktop Trash 规范自行实现

依据 [Trash Specification 1.0](https://specifications.freedesktop.org/trash/latest/)，与 Nautilus、`gio trash` 写同一套结构，文件管理器里能看到并还原。

- **选回收站目录**：文件与 `$XDG_DATA_HOME`（默认 `~/.local/share`）在同一设备上时用 `$XDG_DATA_HOME/Trash`。否则找文件所在挂载点 `$topdir`（按 `/proc/self/mountinfo` 取最长前缀匹配的挂载点，与文件管理器的口径一致；不按 `st_dev` 逐级上溯，因为 btrfs 子卷的 `st_dev` 与所在挂载点不同，会把回收站建在子卷根上，文件管理器看不到）：`$topdir/.Trash` 存在、不是符号链接且有 sticky 位时用 `$topdir/.Trash/$uid`；否则用 `$topdir/.Trash-$uid`，不存在就创建（权限 700）。
- **不跨设备复制**：规范允许跨设备时复制到 home 回收站，但图片库常在独立数据盘上（本机的 `/data` 就和 home 不在同一设备），复制会很慢，还会占用 home 分区。两种 topdir 方式都不可用时拒绝移动、报错，不删除文件。
- **写入顺序**：先以 `O_EXCL` 在 `info/` 创建 `<name>.trashinfo`，重名就在文件名后加序号重试，成功后再把文件 `rename` 到 `files/` 下的同名文件。`.trashinfo` 内容为 `[Trash Info]`、`Path=`（按 RFC 2396 百分号编码；home 回收站写绝对路径，topdir 回收站写相对 `$topdir` 的路径）和 `DeletionDate=YYYY-MM-DDThh:mm:ss`（本地时间）。
- `rename` 跨越 btrfs 子卷等边界会报 `EXDEV`，此时如实报失败、不改为复制。
- 目录与文件一样整体 `rename` 进 `files/`。不维护 `directorysizes`：它只是文件管理器显示回收站大小的缓存，规范允许缺失。
- 不调用 `gio trash`：服务器版 Ubuntu 可能没有它，而按规范实现只有几十行、可以在临时目录里测试。

### macOS：调用系统 `/usr/bin/trash`

- 系统自带的 `/usr/bin/trash` 会把文件移进当前用户对应卷的回收站，可以一次传入多个路径，按批调用以减少进程开销。
- 这个命令出现的版本说法不一：Sequoia 的 man page 写 macOS 14 引入，Tahoe 的 man page 写 macOS 15 引入，有人在 14.6.1 和 14.8 上实测没有（[来源](https://mjtsai.com/blog/2025/08/26/the-trash-command/)）。因此按“macOS 15 起可用”处理：找不到该命令就报错退出，不回退到直接删除。
- 已知问题：用它删除后 Finder 窗口可能显示错乱，关闭重开窗口即恢复，不影响结果。
- 测试不调用真实命令（2026-11-23）：`/usr/bin/trash` 移动到的是用户真实的废纸篓，无法指向临时目录。脚本读环境变量 `DEDUPE_IMAGES_MAC_TRASH` 换命令路径，测试在 macOS 上把它指向替身脚本，把文件移进与 Linux 相同的临时 `<xdg>/Trash/files`，两个平台共用同一组断言；只有 `.trashinfo` 的断言限定在 Linux。此前测试只在 Ubuntu 上写，在 macOS 上运行会把临时文件移进用户的废纸篓并断言失败。
- 不选 `osascript` 调用 Finder：需要用户给终端授予控制 Finder 的自动化权限，并且逐个文件驱动 Finder 很慢。不选 `ctypes` 调用 `NSFileManager trashItemAtURL`：实现复杂，也不好测试。

## 执行流程

0. **clean**（`dedupe_images.py clean <总目录> [--apply]`）：先清理非图片杂项（见“非图片杂项”），减少 plan 要比对的非图片文件不一致。
1. **plan**（`dedupe_images.py plan <总目录> --out <计划.json>`）：脚本扫描并输出计划 JSON，内容包括目录级移走项（`dir_removals`）、不自动处理的包含关系（`dir_review`）与案例（`cases`），每个目录（相对总目录的路径）的重复组（保留项、待删项、体积、哈希、保留项的改名目标）、需人工确认的体积相同哈希不同项，跳过的软件目录，以及汇总（组数、待删文件数、可释放字节数）。终端摘要按一级目录汇总删除与改名数，明细只在 JSON 里，避免上千个目录逐行刷屏。模型用 `show --sample` 抽查自动部分，无问题直接执行 apply，有问题停下报告。
2. **apply**（`dedupe_images.py apply <计划.json>`）：脚本读取同一份计划，先处理目录级移走项：目录里不能出现子目录，非隐藏文件清单须与计划完全一致，每个文件的体积与哈希、保留目录中对应文件的体积与哈希都与计划一致，才整目录移入回收站；移走后逐级删除变空的上级目录（只用 `rmdir`，不删总目录本身）。先移目录是因为复核依赖保留目录里的对应文件，而文件级去重可能移走其中一份（内容仍在保留目录里另一份文件中）。再处理文件级各组，删除前逐个复核：保留项仍存在且哈希未变，待删项的体积和哈希与计划一致。任何一项不符就跳过这一组并在结果里列出，不按过期的计划删除。复核通过的文件移入回收站，这一组全部移走后再执行改名，改名前再检查一次目标不存在，已存在就放弃改名并列出。最后输出成功、跳过和失败的清单；有失败项时退出码为 1，计划不可读、版本不符或平台不支持时为 2 且不动任何文件。
3. **案例**：模型用 `show` 读材料判断（案例多时分批交子 agent），把建议列表给用户确认，按确认结果写决策文件，运行 `dedupe_images.py apply-decisions <决策.json>`（见“案例”）。

## 关键决策

- **用哈希代替看图**：用户问是否要判断图片内容（如下半部分损坏）。体积和哈希都相同的文件逐字节一致，好坏完全相同，看图不会改变保留结果。视觉检查每张约一千到一千六百个输入 token，上千张图就是数百万 token，结果还无法复现；哈希只需读文件，结果确定。因此不做视觉检查。
- **同体积不同内容按字节特征判定损坏**（2026-11-20）：首版假设“截断损坏的图片体积变小、会被体积条件排除”，在 `Comic-BW-byAuthor` 上不成立。该库的 32 组同名同体积不同内容中，31 组是一份完好、另一份含成片 4 KiB 对齐的 0 字节（下载时先按完整体积占位、数据未写全，显示为灰块），其中 7 份连 JPEG 结束标记也缺失；10 组坏的恰是不带序号的原名文件，按名称规则会留下坏图。剩下 1 组两份都缺结束标记、判不出好坏。于是加入只读字节的损坏判定：压缩格式的熵编码数据里不会自然出现 4 KiB 全 0，误判风险低；未压缩格式（bmp、tif、raw）的纯黑区域可能就是 0，不参与。它只在同体积不同内容时作为取舍依据，不对单独的文件或体积不同的文件下结论。
- **以哈希为安全网，放宽命名识别**：因为最终以哈希判定，命名模式宁多勿漏，分组过宽只多算几个哈希，不会误删内容不同的文件。为同一理由，主名忽略大小写和 Unicode 规范形式，同格式扩展名归一。哈希只保证不丢内容，不保证不破坏页码顺序，页码序列因此另有规则（见下条）。
- **`(n)` 在页码序列里按页码处理**（2026-11-20）：在 `pic_dup_to_2T` 实测中，`(n)` 被当作副本标记，使整套页码落进同一名称组，任意两页内容相同就会被删：`Razor Rider` 第 33–42 页两两相同，会删 5 页，留下页码空缺；`吉川先生` 的第 24、46 页是同一张插页；`Amusteven/Cold Assassin` 的两套编号是不同版本，只有 2 页恰好相同，删掉会让另一版本缺页。同时 `Amusteven` 下 30 个目录确实各存了两套逐字节相同、编号错开一位的完整页面（约 2.3 GB），需要保留去重能力。用“两套编号格式 + 补零一套 90% 覆盖”区分整套重复与零星相同：真实数据中整套重复的覆盖率都是 100%，`Cold Assassin` 只有 3%。阈值“4 个不同页码”的代价是同一文件被下载 4 次以上（`a (1)…a (4)`）时也会按序列处理，只在同一序号内去重；这比误删页面的代价小。
- **整套重复只认补零/不补零两种写法**：单一编号格式内无法区分“作品本身的重复页”和“两套编号相撞”。已知漏判：两套编号从 100 起写法相同、互相覆盖后，末尾多出的一页（如 `Mad Alyss 6` 的 `page (114)` 与 `page (113)` 相同）不移走。
- **跨名称匹配按“整套”而不是逐对判定**（2026-11-21）：对 `pic_dup_to_2T` 做目录内全量哈希比对，计划之外还有 5805 组同内容文件（约 7.3 GB）。按命名形态分为四类：只差补零（Vchan (1-7) 一个目录 922 对）、只差开头流水号（`[Artist] Vadass` 三个目录各约一半、Tamagou 整本存了两遍）、两种命名整套对应（Amusteven/Velna 10 个目录 `01.jpg` 对 `page (001).jpg`，Distress Signal 编号错开一位，`桜の灯る日へ (41510503)` 的 `(1)` 一套错开 5 位，Dotapun 后半段错位），以及同一编号内的重复页与 Pixiv 重复投稿（942 个，作品本身的内容，不动）。哈希只保证不丢内容，不保证不缺页，所以除补零外都要求整套：流水号一类在真实数据中整套重复的目录待删占比约 50%，零星配对的不到 10%，阈值取 25%；模板一类最初取 4 个文件，结果把 `DUAL LOVE [English & Korean]` 韩版的 6 张封面（与英版相同）当整套移走，改为至少 10 个文件并要求两套数量相近，`HitmanX3Z Sets/Art` 画集里 9 张一套的小套因此放过。整套比对用目录内全部文件分套、已被名称组移走的文件算已覆盖，否则 Dotapun 这种大部分同名配对、后半段错位的目录剩下两套数量对不上。真实库上新增待删 4264 个（约 4.6 GB）。
- **目录级重复：内容相同与同名子集自动移走，改名子集只报告**（2026-11-21；2026-11-22 起内容相同但文件名不同的也改为交模型判断）：同一库中按哈希确认的包含关系有 1987 对（90% 覆盖口径），涉及 702 个候选目录约 115 GB，绝大多数不是 `X`/`X (2)` 这种兄弟副本，而是名字不同的同内容目录、跨父目录的副本，以及子集。用户选择三类都自动处理，讨论后把子集拆开：文件名改过的子集会丢失组织信息——`黄蓉襄阳后记 13`（104 张）在合集 `黄蓉襄阳后记1-21` 里是 `0948_00000944.jpg…`，移走后章节边界与标题消失；`(1-5上)` 的 `551_72.png` 等带话数页码的文件名在 `(1-5.5)` 里是纯流水号；`Velna/Deluxe Edition/` 下的各版本子目录分别被别处吞掉，版本归档结构被拆散；`[NTRMAN] Tomato/ENG`（`01…41`）只因杂图包缺一页才没被不补零命名、混在杂图里的 `Tomato_1.jpg…` 替换。文件名原样存在的子集（`DUAL LOVE - Part 1` 38 张 ⊂ `[Laliberte] DUAL LOVE - Part 1` 41 张）是同一份东西的不完整版，移走几乎无损。100% 覆盖口径下改名子集 444 对、同名子集 181 对。要求 100% 包含是因为自动移走必须不丢图片，分析时 90% 口径的配对里就有 Tomato 这种缺页的。只移走没有子目录的目录：整目录移入回收站会连带子目录，而子目录可能正是保留目录。保留顺序中“目录名更长优先”是经验规则，同内容不同名的目录说不清谁的名字更好，长名字通常多了作者、汉化组或画廊号；结果可能留下用户不喜欢的名字，但不丢内容。首版按目录逐个取舍，实测 472 个移走项中 143 个会拆散合集：`[smallflyingrat (小飛鼠)] 黄蓉襄阳后记/` 64 个子目录移走 63 个而保留在另一个大合集里，`Mad Alyss 1-6/` 与 `Mad Alyss/Comic/` 互相拆（第 1 话留在一边、第 2 话留在另一边），两个合集都不再完整。于是保留顺序加入父目录子目录数，并把会拆散合集的移走降为人工确认：整个合集重复或兄弟副本照常移走，两个合集大部分相同（63/64）这类由用户决定。改后自动移走 337 个目录（59.9 GB，内容相同 249 个、同名子集 88 个），人工确认 306 个（会拆散合集 135、改名子集 162、含子目录 9）。
- **同名子集要覆盖保留目录 90% 才自动移走**（2026-11-22）：新流程首次抽查发现，“文件名原样存在的子集就是不完整副本”不成立。88 个同名子集按占保留目录的比例排开，低端是独立作品被并进大目录：`[NTRMAN] Icecream ( EN )`（13 张 `Spill_*`）与 `Tutor ( EN )`（14 张 `ml2_*`）在 481 张的 `[PATREON] NTRMAN` 杂图包里，`HitmanX3Z Sets/Sabrina`、`Sci-Fi` 等在 1789 张的 `Art` 里，`陵辱連鎖 02`、`03` 在名为 `01` 实装 1–3 话的目录里，`合租女室友 8`、`DUAL LOVE - Part 1`、`淫母日记3` 等单话在合集里（2%–40%）；高端（90% 以上）都是同一作品缺几页的副本（`PARASITE` 51/54、`Freeloader` ⊂ `My Best Friend` 22/23）。比例按去重后的哈希算，因为部分保留目录自身存了两套编号（`[Artist] Vadass` 按文件数只有 50%）。
- **弱标记要求主名文件存在**：`IMG_0001.jpg` 这类正常命名会被 `_n` 模式剥离。剥离后的文件即使内容相同、删掉也不丢数据，但会丢掉一个用户可能在用的文件名，所以只有原名文件确实存在时才把它们当副本。
- **脚本管有把握的、模型管要理解的**（2026-11-22 用户提出）：此前脚本把拿不准的一律报给用户，或用阈值硬判；前几轮的误删（页码、`DUAL LOVE` 封面、拆散合集）都是看文件名和目录结构才发现的。改为：确定性规则留在脚本，命名、版本、合集结构上的取舍交模型，模型的决定只能是 `move`、`trash`、`keep` 这几种操作（后来加了 `trash_matching`），由脚本按哈希校验“不丢内容”后执行。自动部分不再等用户确认（文件进回收站可还原、执行前逐个复核），但模型须先按固定清单抽查，发现问题就停下，因为那说明规则有漏洞，应修脚本而不是临场绕过。脚本仍可脱离 agent 独立使用。合并两个合集需要移动目录，所以加了 `move`；不做目录改名，内容相同时选保留哪一边就决定了名字。读图片分辨率不做：案例都是按哈希确认的包含关系，两边图片逐字节相同。`pic_dup_to_2T` 上改后自动移走 307 个目录（57.0 GB：内容相同且同名 219、同名子集 88），文件级待删 6648 个（7.5 GB）；案例 176 个、全部是目录案例，覆盖 336 对包含关系（会拆散合集 117、内容相同但文件名不同 39、改名子集 175、含子目录 5），最大的一个是两个黄蓉合集之间的 64 对，其中 63 对小合集 ⊂ 大合集、1 对方向相反，正是需要合并而不是单纯移走的情形。
- **Python 3.14+ 标准库**：沿用本仓库用户级 skill 的运行时约定（见 README），以 `python3` 调用，不引入第三方依赖。不为系统自带 Python 降低版本下限：macOS 默认没有完整 Python，Command Line Tools 附带的是 3.9；Ubuntu 各版本自带版本不一；测试只在 3.14 上运行，更低版本的兼容性无从保证。按 README 用 uv 安装 3.14 即可满足。
- **看图只作最后手段**：2026-11-20 用户不要 agent 看图；2026-11-22 改为只对少量案例看图（每次最多 10 个）。真实库唯一判不出的 `171.jpg`/`171 (1).jpg` 逐字节对比后，两份只有开头 8949 字节不同，副本那段全是 0（文件头都没了），原件则因缺 `FFD9` 也被判为损坏，两份都“损坏”才判不出；加了清零规则后不用看图。剩下需要看图的只有不同字节在图像数据里、两边都非 0 的情况，真实库目前没有。
- **单独存在的副本也改回原名**（2026-11-20 用户要求）：去重只是一部分，图片库里“只剩 `a (n).jpg` 而没有 `a.jpg`”的情况同样是命名残留。这类文件没有重复组，不经过哈希这道安全网，因此另加序号小于 1000 的条件，避免把年份当序号。它们在计划中是 `remove` 为空的组，复核只核对体积、不算哈希：改名可逆，而单独副本可能很多，逐个哈希会让 plan 和 apply 各多读一遍这些文件。
- **递归、且不定义“底层图片目录”**（2026-11-20）：首版只处理一级子目录，按作者/作品分层的漫画库（`Comic-BW-byAuthor`：35 个作者、1263 个含图目录，深度 3 到 10 层不等，还有 1390 张图与子目录并存的目录）只能逐个作者调用。由于每个目录只比较自身的直接文件，递归不引入跨目录判定，所以直接把每个目录当作处理单元，不需要“底层”判定，也不漏掉中间层的图片。替换原来的一级模式、不设开关：只有一层子目录的库行为基本不变，差别只是总目录本身的图片也会处理。
- **跳过软件目录**：同一个库的 `NTRMAN/NTRMAN/` 下是一批游戏（1100 个 dll、31 个 exe、149 个 `.assets`）。游戏素材被改名或删除可能让游戏无法运行，而单独副本改名没有哈希兜底，因此按程序文件识别软件目录、整棵子树跳过。真实库里这些游戏目录当时没有命中任何规则，这一条是预防。
- **弱标记分组在真实库中基本不产生噪声**：同一个库里 56 个由弱标记形成的名称组（多为 `00.jpg`、`00_1.jpg`、`00_2.jpg` 这类封面变体）只有 3 处体积相同，且都逐字节一致，是真正的重复；体积不同的直接放过，不进人工确认。因此不为弱标记另设规则。
- **先出计划、确认后执行、执行前复核**：删除不可逆（回收站可能被清空），计划和执行之间目录也可能被改动，所以 apply 不重新扫描定夺，只执行计划中仍然成立的部分。改名会让外部按路径引用该文件的图库软件、相册或同步工具失去对应，这是改名本身的代价，脚本不做探测。

- **单章拼成合集时留单章、删合集**（2026-11-22 用户要求）：单章加起来与合集图片数相同、哈希一致时，删合集、保留单章，单章不在同一父目录下的集中到一个父目录。集中的做法是把单章移进合集目录、再用 `trash_matching` 移走合集自己的图片，合集目录就成了单章的父目录、名字不变，不用新增建目录的操作。单章有重叠或只覆盖一部分时不动（`pic_dup_to_2T` 中 29 个单章与合集的组合里只有 `淫母日记 1-3 (1) x` 严格拼成；两个 Tanya 合集按集合相同但含重复图、单章散在别的合集里，不算）。
- **非图片杂项按固定清单清理，不含 txt**（2026-11-22 用户要求）：`pic_dup_to_2T` 中非图片文件共约 400 个。用户点名删除 txt、opf、Thumbs.db、`.bc!`，并同意模型提出的其余几类；后来决定纳入 skill 时把 txt 排除，因为真实库里 11 个 txt 中有 2 个是作品的人物简介与世界观设定。`._*` 只认 AppleDouble 魔数：真实库 269 个 `._*` 大多带 `.jpg` `.png` 扩展名，按扩展名会被当成图片，统计时一度只数出 2 个；全是 4 KiB 以内的元数据。残缺下载要单列“没有完成文件”的：`Fansadox collection 37 - Psycho` 整个目录 47 个文件都是 `.bc!`，清理后整部作品没了，两个 `.!qB` 让 Amusteven 两部作品各缺一页。pdf、mp4、cbr 是作品本体，不处理。做成子命令而不是另一个脚本，是为了复用回收站实现与软件目录判定。
- **合并合集的经验**（2026-11-22，C 类案例）：用户确认了 13 个合集对的合并方案，从中写进 SKILL.md 的有三条。一是保留偏好：按章节分子目录的优于平铺（`黄蓉襄阳后记1-21` 平铺 1922 张整个在分章大合集里，`猫眼之纯蓝欢欲 1-2` 只多 1 张，移进分章版后移走），已有整理好的总合集时把散落版本并进去（`淫母日记 1-2 x`、`3 x`、`4（含Textless）` 并进 `淫母日记 xx`，共移入 6 张独有图）。二是“含子目录”的配对只比较了一层：`Mad Alyss 1-6` 中 2、3、5 话的一层图片与别处同名目录相同，但下级 `1-Standard`、`2-Textless version` 等有 480 张别处没有，整目录 `trash` 被 `apply-decisions` 整案拒绝，改为 `trash_matching`。三是先试跑：方案阶段为算各方独有的图片临时写了哈希比对脚本，这正是 `apply-decisions` 校验已经在算的，于是加 `--check` 把它暴露出来。
- **独立作品与杂图包：删杂图包里的重叠图片**（2026-11-22 用户要求）：独立作品（命名、组织好的单本）被画师杂图包、Patreon 包、Pixiv 合集、汇总目录包含时，保留独立作品，用 `trash_matching` 删掉杂图包里与之相同的图片（同一张有多份一起删），杂图包其余内容不动。单行本、系列合集不算杂图包（删页会拆坏书），两边都是画师合集、分不出哪个是独立作品的也不算。首次执行从 5 个杂图包删掉 862 张、约 1.0 GB。
