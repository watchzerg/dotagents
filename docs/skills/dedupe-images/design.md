# dedupe-images 设计说明

维护 [`skills/dedupe-images`](../../../skills/dedupe-images/SKILL.md) 前先读本文。精确规则与阈值以 [`scripts/dedupe_images.py`](../../../skills/dedupe-images/scripts/dedupe_images.py) 的常量与函数说明为准；案例判断规则与决策文件格式以 SKILL.md 为准；本文只记取舍及其依据。文中的真实库指 `Comic-BW-byAuthor` 与 `pic_dup_to_2T`。

## 目标与边界

- 对用户给出的总目录递归去重：每个目录（含总目录本身）内找同名带副本标记、内容相同的图片，留一张、其余进回收站，副本改回原名；同一批图片以两种文件名各存一份的按命名对应识别；一个目录的图片全部在另一目录里的整目录移走。
- 文件级只比较目录直接包含的图片，跨目录同名同内容的单个文件不算重复；不区分“底层目录”，既有图片又有子目录的目录同样处理。
- 不做相似图片识别（不同分辨率、压缩或文件名的同一张图）。
- 脚本可脱离 agent 独立使用。

## 核心原则

- **脚本管有把握的、模型管要理解的**（2026-11-22 用户提出）：前几轮误删（页码、`DUAL LOVE` 封面、拆散合集）都是看文件名和目录结构才发现的，阈值硬判兜不住。确定性规则留在脚本；命名、版本、合集结构上的取舍整理成案例交模型，模型只能写 `move`、`trash`、`trash_matching`、`keep`，由脚本校验后执行。
- **哈希是安全网**：任何路径下被移走的文件都必须在保留处有 SHA-256 相同的文件，模型判断失误最多留错名字或结构，不丢图片。哈希只保证不丢内容、不保证不缺页，所以页码与整套规则另有约束（见下）。
- **用哈希代替看图**：体积与哈希相同即逐字节一致，看图不会改变结果；视觉检查每张约一千到一千六百 token，上千张就是数百万，且不可复现。看图只作最后手段：仅文件案例、每次最多 10 个。真实库唯一判不出的 `171.jpg` 加了清零规则后也不用看图，看图流程尚未实际走过。
- **自动部分抽查后直接执行**：进回收站可还原，apply 前逐项复核；但模型须先按固定清单抽查，发现问题就停下修脚本，而不是临场绕过。
- **先出计划、执行前复核**：plan 与 apply 之间目录可能变动，apply 不重新扫描定夺，只执行计划中仍成立的部分（目录内容、体积、哈希、保留项都与计划一致，改名前目标仍不存在），不符的跳过并列出。apply 先处理目录级再处理文件级，因为目录级复核依赖保留目录里的对应文件，而文件级去重可能移走其中一份。改名会让按路径引用文件的外部软件失去对应，这是改名本身的代价，不做探测。

## 规则与依据

### 扫描范围

- 跳过隐藏项（挂载点下的 `.Trash-<uid>`，外置盘上的 `._*` 与 `.DS_Store`）与符号链接（不跟随，不会循环）。
- 跳过软件目录（`PROGRAM_EXTENSIONS` 或 `.app`）及其整棵子树：真实库 `NTRMAN/NTRMAN/` 下是一批游戏，改名或删素材会让游戏无法运行，而单独副本改名没有哈希兜底。总目录本身不按此跳过，根下零星一个 `exe` 不应让整个库被跳过。
- 递归且不定义“底层目录”（2026-11-20）：按作者/作品分层的库深度 3 到 10 层不等，还有图片与子目录并存的目录。每个目录只比较自身直接文件，递归不引入跨目录判定。

### 名称组与副本标记

- 强标记覆盖浏览器下载、Windows/macOS/GNOME 复制、Dropbox 冲突副本与 wget 等写法，可叠加，总是参与分组；弱标记（`a-1`、`a_1`、`a 2`）常见于正常命名（`IMG_0001.jpg`），只有剥离后的主名文件存在时才算副本，避免丢掉用户在用的文件名。真实库 56 个弱标记名称组只有 3 处同体积，且都逐字节一致，不另设规则。
- 命名识别宁多勿漏：分组过宽只多算几个哈希。主名按 NFC 与 casefold 归一，同格式扩展名归一。

### 同体积不同内容：损坏判定（2026-11-20）

首版假设“截断损坏的图片体积变小、会被体积条件排除”，在真实库不成立：32 组同名同体积不同内容中 31 组是一份完好、另一份含成片 4 KiB 对齐的 0（下载时先占位、数据未写全），10 组坏的恰是原名文件，按名称规则会留下坏图。于是只对压缩格式读字节判损坏：熵编码数据里不会自然出现 4 KiB 全 0；未压缩格式的纯黑区域可能就是 0，不参与。另加清零副本规则：两份都缺结束标记时（`171.jpg` 副本开头 8949 字节全 0），不同字节在一方全为 0 即为它的清零副本。判定只在同体积不同内容时作为取舍依据，不对单独文件下结论；判不出的成为文件案例。

### 页码序列（2026-11-20）

`page (1)…page (95)` 与下载副本 `(n)` 同形，整套会落进同一名称组，任意两页相同就被删：`Razor Rider` 会删 5 页留下空缺，`Cold Assassin` 两个版本恰有 2 页相同。同时 `Amusteven` 下 30 个目录确实各存了两套编号错开一位的完整页面（约 2.3 GB）。因此：

- 最内层序号有 `SERIES_MIN_PAGES` 个以上取值视为页码，只在同一页码内去重。代价是同一文件下载 4 次以上也按序列处理，比误删页面小。
- 不同页码的同内容文件只在补零与不补零两套整套重复（覆盖 `WHOLE_SET_RATIO`）时移走不补零一套：真实数据整套重复的覆盖率都是 100%，`Cold Assassin` 只有 3%。单一编号格式内无法区分作品自身的重复页与编号相撞，一律不动。
- 序列内不改名（剥离后会变成 `page.jpg`）。
- 已知漏判：`page (100)` 起两种写法相同，末尾多出的一页（`Mad Alyss 6` 的 `page (114)` 与 `(113)`）不移走。

### 跨名称匹配（2026-11-21）

真实库计划之外还有 5805 组目录内同内容文件（约 7.3 GB），分为只差补零（`zero_pad`）、只差开头流水号（`index_prefix`）、两套命名模板整套对应（`name_set`），以及作品自身的重复页与重复投稿（不动）。都要求体积与哈希相同，不做损坏判定、不改名。

- 只差补零不要求整套：作品不会用两种补零写法排同一页。
- 流水号要求待删占目录 `INDEX_SET_RATIO`：整套重复的目录约 50%，零星配对多是合并章节时每章重复的声明页（不到 10%），删掉会让后面章节缺页。
- 模板整套最初只要求 4 个文件，结果把 `DUAL LOVE` 韩版 6 张与英版相同的封面当整套移走；改为 `NAME_SET_MIN_FILES` 且两套数量相近（`SET_SIZE_RATIO`）。前面规则已移走的文件算已覆盖，否则大部分同名、后半段错位的目录剩下两套数量对不上。

### 目录级重复（2026-11-21、11-22）

真实库按哈希确认的包含关系涉及约 115 GB，多数不是 `X`/`X (2)` 兄弟副本，而是改名的同内容目录、跨父目录副本与子集。自动移走只限“同一份东西的副本”，其余进 `dir_review` 并整理成案例：

- 要求 100% 包含：90% 口径下就有缺页的配对（`[NTRMAN] Tomato`）。
- 改名子集只交模型：文件名改过会丢组织信息（`黄蓉襄阳后记 13` 在合集里是流水号，移走后章节边界与标题消失；`Velna/Deluxe Edition/` 的版本归档被拆散）。内容相同但文件名不同的也交模型，留哪边就是留哪套名字（2026-11-22）。
- 同名子集须覆盖保留目录 `SUBSET_COVER_RATIO`（按去重后的哈希，保留目录自身存两套编号时不拉低比例）：低比例的是独立作品并进杂图包、单话在合集里，高比例的才是缺几页的副本。
- 只移走没有子目录、没有符号链接、非图片文件在保留处同名同内容的目录：整目录进回收站会连带子目录（可能正是别处的保留目录）和只在副本里有的说明文件或未完成下载。
- 不拆散合集：首版 472 个移走项中 143 个会拆散合集（`黄蓉襄阳后记/` 64 个子目录移走 63 个；`Mad Alyss 1-6/` 与 `Mad Alyss/Comic/` 互相拆）。保留顺序加入父目录子目录数，使两个合集之间方向一致；非兄弟且父目录会留下其他子目录的降为案例。
- “目录名更长优先”是经验规则（长名字通常多了作者、汉化组或画廊号），可能留下用户不喜欢的名字，但不丢内容。

### 案例与决策

- 跨父目录的包含关系按父目录对合成一个案例：两个合集之间的取舍要整体决定。
- 合集恰好由单章拼成（`composed`，2026-11-22 用户要求）：删合集、留单章，散落的单章集中到合集目录（先 `move` 进去再 `trash_matching`），合集目录名不变，不用新增建目录的操作。只认严格拼成：真实库 29 个单章与合集组合只有 1 个满足。
- `move` 为合并合集而加；不做目录改名，选保留哪一边就决定了名字。`move` 的 `name` 用于把流水号版独有的图按位置并入命名版（`合租女室友` 59 张）。
- `trash_matching`：`Mad Alyss 1-6` 的一层图片与别处相同，但下级有 480 张别处没有，整目录 `trash` 被整案拒绝；杂图包也只需删重叠部分（首次执行从 5 个杂图包删 862 张）。
- `apply-decisions --check`：合并方案阶段曾临时写哈希脚本算各方独有的图，这正是校验已在算的。`--check` 按顺序模拟，后面案例用到前面将移走或移动的路径时报冲突，否则 A 保留 B、B 保留 A 都会通过、执行时才跳过第二个。真实执行时每个案例重新计算哈希，因为前面的案例可能已把某路径换成别的文件。
- `show` 用「」显示首尾带空白的路径：`黄蓉襄阳后记/` 下章节目录名是 ` 01`，子 agent 照抄成 `01`，整案因路径不存在被跳过。
- 案例判断规则中的作品内部结构重复、杂图包后续配对、编号连续图集保留，都来自用户对真实库案例的逐类决定。

### 保留与改回原名

- 单独存在的副本（只有 `a (n).jpg` 没有 `a.jpg`）也改回原名（2026-11-20 用户要求）：同样是命名残留。没有哈希兜底，所以要求各层序号小于 `RENAME_NUMBER_LIMIT`（`Trip (2019).jpg` 不改），复核只核对体积（改名可逆，逐个哈希会让 plan 和 apply 各多读一遍）。
- 名称组还有体积不同或判不出取舍的文件时不改名：说不清谁该拿原名。
- 原名以分隔符结尾时不改（2026-11-22）：`page - (n)` 一套被跨名称匹配移走后只剩 `page - (1).jpg`，原规则会改成 `page -.jpg`。

### 非图片杂项（`clean`，2026-11-22）

- 按固定清单清理，不含 txt：真实库 11 个 txt 中 2 个是人物简介与世界观设定。pdf、mp4、cbr 是作品本体，不处理。
- `._*` 只认 AppleDouble 魔数：真实库 269 个 `._*` 多带 `.jpg` 扩展名，按扩展名会被当成图片。`.ico` 因此不在图片扩展名里。与 plan 不同，clean 不跳过隐藏文件（`._*`、`.ehviewer` 正是隐藏的）。
- 残缺下载单列“没有完成文件”的：`Fansadox collection 37 - Psycho` 47 个文件全是 `.bc!`，清理后整部作品没了。
- 做成子命令是为复用回收站实现与软件目录判定。

## 回收站

### Linux：按 FreeDesktop Trash 规范自行实现

依据 [Trash Specification 1.0](https://specifications.freedesktop.org/trash/latest/)，与 Nautilus、`gio trash` 写同一套结构。

- 挂载点按 `/proc/self/mountinfo` 最长前缀匹配，不按 `st_dev` 上溯：btrfs 子卷的 `st_dev` 与挂载点不同，会把回收站建在子卷根上，文件管理器看不到。
- 不跨设备复制：图片库常在独立数据盘，复制慢且占 home 分区。topdir 回收站不可用、或 `rename` 报 `EXDEV` 时如实报失败，不删除。
- 先以 `O_EXCL` 建 `.trashinfo` 再 `rename` 文件；不维护 `directorysizes`（文件管理器的显示缓存，规范允许缺失）。
- 不调用 `gio trash`：服务器版 Ubuntu 可能没有，自行实现只有几十行、可在临时目录测试。

### macOS：调用系统 `/usr/bin/trash`

- 引入版本说法不一（man page 写 14 或 15，有人在 14.6.1、14.8 上实测没有，[来源](https://mjtsai.com/blog/2025/08/26/the-trash-command/)），按 macOS 15 起可用处理；找不到就报错退出，不回退到直接删除。按批调用以减少进程开销。删除后 Finder 窗口可能显示错乱，重开即恢复。
- 不选 `osascript` 驱动 Finder（需要自动化授权，逐个文件很慢），不选 `ctypes` 调 `NSFileManager`（复杂、难测）。
- 测试不调用真实命令（2026-11-23）：它移到用户真实的废纸篓，无法指向临时目录。脚本读 `DEDUPE_IMAGES_MAC_TRASH` 换命令路径，测试在 macOS 上指向替身脚本，把文件移进与 Linux 相同的临时 `<xdg>/Trash/files`，两平台共用断言，只有 `.trashinfo` 断言限 Linux。

## 调用方式

- **只允许用户调用**（2026-11-25）：设 `disable-model-invocation: true`，description 只作给人看的一行摘要。会把文件移入废纸篓，且只由用户主动发起；没有其他 skill 调用本 skill，不必在所有项目常驻上下文。

## 运行时

只依赖 Python 3.14+ 标准库，沿用本仓库用户级 skill 的约定。不为系统自带 Python 降低下限：macOS Command Line Tools 附带 3.9，Ubuntu 各版本不一，测试只在 3.14 上运行。
