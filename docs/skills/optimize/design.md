# optimize 设计说明

`skills/optimize` 尚未实现，本文是动手前的设计结论。实现和后续维护前先读本文。记录目标、关键决策、与其他 skill 的耦合和待验收项，只写代码与 git 历史看不出的意图。

## 目标与边界

把“调研 → spec → 拆票 → 实施 → 合并清理”这条项目优化流水线合成一次调用，人工确认从每轮 5～6 次减到 1 次。一条流水线带三个主题：

- `/optimize arch`：框架结构与代码分层。
- `/optimize docs`：文档结构，即单页过大、职责不清、难以按需发现。
- `/optimize logs`：日志缺失与冗余。

不带主题时列出可选项。带 spec 编号调用时续跑。

不做的事：

- 不做功能开发。功能的 spec 需要逐项追问产品决策，不能压成一次确认。
- 不合并 `prune-tests` 与 `docs-audit`，理由见关键决策。
- 不做“一次跑完全部主题”的入口，理由见关键决策。
- 不推送。`git push` 留给用户。

## 来源

2026-11-13 读取了 bangou、media-glance、x-media-saver 三个项目 2026-10-12 至 11-12 的会话，统计用户在各确认点的实际回答。数字来自子 agent 的汇总，没有逐条复核原始会话。

| 确认点 | 用户的实际回答 | 处理 |
| --- | --- | --- |
| to-spec 的 seam 确认 | 约 15 次，几乎全是确认或选推荐项；模型每次都提议沿用现有 seam | 并入唯一的一次确认 |
| to-tickets 的拆票确认 | 从不回答问题，每次贴同一句“自己 review 大票、自闭环、依赖” | 改为固定步骤 |
| 票据自审 | 核实过的每一轮都改了票（20→10、18→22、20→25 等） | 保留，交给独立子 agent |
| implement-spec 中途 | 基本零输入，连续运行 50～110 分钟 | 不变 |
| 结尾的待裁决项 | 全部是“按你的建议处理” | 默认按推荐，报告列出 |
| 合并与清理 | 每次同一句话 | 写进流程 |
| 调研报告之后、建 spec 之前 | 范围取舍与只有用户知道的事实，集中在这里 | 保留这一次 |

最后一行的实例：“日志先不加”“全部三档”“我从来没决策过不写日志”；NAS 暂时无法挂载所以把一张票拆出去、旧部署已切换、某个库可丢弃。

## 关键决策

- **只停一次，停在建 spec 之前**：调研结束后把范围建议、测试 seam、需要用户提供的事实一次问完，之后运行到结束。依据见来源表。调用时带“不要问我”则连这一次也跳过：按推荐执行，所做假设记进 spec。用户十月用 `/goal` 以同样的授权跑过四轮架构票，可行。
- **一个 skill 带主题参数，不做三个 skill**：三个主题只在调研指令、入选门槛和验证方式上不同，spec、拆票、实施、合并完全相同。`SKILL.md` 只写编排与停止规则，各主题和各阶段的做法放 `references/` 按需读取。
- **不做一次跑完全部主题的入口**：架构改完后，文档与日志的调研结论就过期，只能串行，每轮 1～4.5 小时；一轮文档优化就有 75 个提交，连跑后一次要审的量太大，前一轮的偏差会被后一轮当成事实。有了本 skill，全做一遍只是依次敲几条命令。
- **日志也走完整流水线**：bangou 与 x-media-saver 的日志优化当时是调研后直接修的。用户 2026-11-13 决定统一走流水线：三个主题结构一致，建票还能留痕。代价是小改动也要走完 spec 和拆票。
- **内化上游三个 skill 的内容，不包装**：`to-spec`、`to-tickets`、`implement-spec` 带 `disable-model-invocation: true`，模型无法调用；按插件路径读它们的正文则路径随版本变化，且正文包含本 skill 要去掉的人工确认。三份合计约 11 KB，保留 spec 模板、纵向切片规则与大范围重构的先扩后收例外、票据模板、实施编排，按 Beads 与 `gate-core`、`gate-full` 改写。上游为 MIT 许可（Matt Pocock），改写的参考文件注明出处。`tdd` 与 `code-review` 可被模型调用，继续引用。
- **票据自审交给没看过拆票过程的子 agent**：自审每轮都改票，必须保留。原先由同一会话自己审自己；改为新子 agent 只拿 spec 与票据草稿，按大票、自闭环、票间依赖三项审。
- **各主题的验证方式分开写**：
  - 架构：每票用 `tdd`，集成分支跑一次无筛选的 `gate-full`。
  - 文档：跑 `docs-check`，不跑 `gate-full`。用户在 media-glance 手动要求过。
  - 日志：不照搬 `tdd`。为日志输出逐条写测试正是 `prune-tests` 会删的那类；只在日志的统一出口留少量测试，其余由 review 核对。
- **入选门槛写成客观标准**：media-glance 连续几轮架构扫描每次都报出新的“strong”候选，用户质疑后模型承认那只是相对排序。各主题的参考文件给出可判定的门槛，调研结果不达标时以“无需优化”结束，不为了产出而建 spec。
- **状态落在票据里，第一步判断阶段**：spec 与票据进 tracker，每个阶段从票据读输入。skill 的第一步固定为根据票据状态判断当前阶段，因此带 spec 编号重新调用即可续跑。会话里出现过三类中断：API 故障、屏幕锁定、上下文压缩。用户原先“建完票 `/clear` 再实施”的做法也因此仍然可用。
- **主 agent 只编排**：调研分发给子 agent 后由主 agent 汇总裁决；每张票一个 worktree 子 agent；合并、review、修复各一个。主 agent 不写产品代码，上下文只留结论。
- **阶段出口用命令验证**：票据依赖无环；门禁检查退出码（出现过合并子 agent 未检查退出码）；收尾时 `git worktree list` 与 `git branch` 只剩 main，票据全部关闭。命令输出写进报告。
- **阻塞的定义写明**：只有三类情况停下：仓库事实互相矛盾且无法判断以谁为准、权限被拒、桌面会话锁定。权限被拒不得换路径绕过（出现过子 agent 改用 `uv tool install` 绕过拒绝）。屏幕锁定立即失败并报告，不等待（media-glance 曾空等约 9 小时）。其余一律按推荐执行并记入报告。
- **合并与清理是流程的一部分，推送不是**：合并进 main、关票、清理 worktree 与分支每次都是同一句指令，写进流程。用户每次手动 `git push`，保持不变。
- **报告格式固定**：代用户做出的决定、与 spec 的偏离、未验证项、遗留票据、出口检查的命令输出。会话里模型每轮都自发列出这些，固定下来便于对照。

## 不合并 prune-tests 与 docs-audit

两者流程短、判断标准固定、不需要 spec 与拆票，并入只会变慢，还会让一个 skill 里并存两套流程。

| | 本 skill | prune-tests | docs-audit |
| --- | --- | --- | --- |
| 回答的问题 | 结构是否合理，哪些值得改 | 哪些测试该删 | 正文与代码是否一致 |
| 判断依据 | 设计取舍，要排序选范围 | skill 内固定的保留标准 | 代码事实，逐条可证伪 |
| 耗时 | 1～4.5 小时 | 15～27 分钟，两次运行均零干预 | 短，适合定期跑 |

衔接方式：

- 架构主题里，测试精简由单独的票按 `prune-tests` 的规则做。bangou 的一轮运行已自发这样做。
- 文档与架构主题收尾时，以集成分支的基准跑 `docs-audit` 的 diff 模式，核对被搬动或受影响的页面。
- 文档主题的调研只看结构。发现正文与代码不符时在报告里建议运行 `/docs-audit`，不纳入本次 spec。
- `prune-tests` 末尾加一步：建一张已关闭的票记录前后用例数与保留范围，使四种优化都有票据留痕。这是对 `prune-tests` 的改动，实现时同步更新它的 design.md。

## 计划的目录结构

```text
skills/optimize/
├── SKILL.md                 # 参数、阶段判断、编排、停止规则、报告格式
└── references/
    ├── topic-arch.md        # 调研简报、入选门槛、验证方式
    ├── topic-docs.md
    ├── topic-logs.md
    ├── spec.md              # spec 模板与 seam 规则
    ├── tickets.md           # 切片规则、票据模板、自审标准
    └── implement.md         # 集成分支、worktree 子 agent、合并、review、出口检查
```

各主题调研简报的起点是用户在三个项目里反复使用的原话，实现时从会话中取。
