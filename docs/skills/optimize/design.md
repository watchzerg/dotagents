# optimize 设计说明

维护 [`skills/optimize`](../../../skills/optimize/SKILL.md) 前先读本文。skill 已于 2026-11-13 实现，尚未在任何目标项目上真实运行。本文只写代码与 git 历史看不出的意图：目标、决策及其依据、与其他 skill 的耦合、待验收项。规则表、模板与步骤以 skill 目录内的文件为准，本文不另存副本。

## 目标与边界

把“调研 → spec → 拆票 → 实施 → 合并清理”这条项目优化流水线合成一次调用，人工确认从每轮 5～6 次减到 1 次。主题 `arch`（框架结构与代码分层）、`docs`（文档结构：单页过大、职责不清、难以按需发现）、`logs`（日志缺失与冗余）；不带主题时列出可选项，带 spec 编号时续跑。

不做的事：

- 功能开发。功能的 spec 需要逐项追问产品决策，不能压成一次确认。
- 并入 `prune-tests` 与 `docs-audit`，见[与 prune-tests、docs-audit 的分工](#与-prune-testsdocs-audit-的分工)。
- 一次跑完全部主题的入口，见关键决策。
- 推送。用户每次手动 `git push`。

## 来源

2026-11-13 读取了 bangou、media-glance、x-media-saver 三个项目 2026-10-12 至 11-12 的会话，统计用户在各确认点的实际回答。数字来自子 agent 的汇总，没有逐条复核原始会话。

| 确认点 | 用户的实际回答 | 处理 |
| --- | --- | --- |
| to-spec 的 seam 确认 | 约 15 次，几乎全是确认或选推荐项；模型每次都提议沿用现有 seam | 并入唯一的一次确认 |
| to-tickets 的拆票确认 | 从不回答问题，每次贴同一句“自己 review 大票、自闭环、依赖” | 改为固定步骤 |
| 票据自审 | 核实过的每一轮都改了票（20→10、18→22、20→25 等） | 保留，交给独立子 agent |
| implement-spec 中途 | 基本零输入，连续运行 50～110 分钟 | 不变 |
| 结尾的待裁决项 | 全部是“按你的建议处理” | 默认按推荐，报告列出 |
| 合并与清理 | 每次同一句话 | 写进流程 |
| 调研报告之后、建 spec 之前 | 范围取舍与只有用户知道的事实，集中在这里 | 保留这一次 |

最后一行的实例：“日志先不加”“全部三档”“我从来没决策过不写日志”；NAS 暂时无法挂载所以把一张票拆出去、旧部署已切换、某个库可丢弃。

### 调研简报的起点

各主题的调研简报以用户实际用过的提示词为起点。原话由子 agent 从会话中摘出，`…` 是摘录时的省略。

| 主题 | 原话 | 来源 |
| --- | --- | --- |
| 架构 | “你帮我整体梳理下当前的项目。从框架结构到代码分层，看下不合理的地方，按改造必要性从高到低排序（影响程度、改造成本等因素）。” | x-media-saver，2026-11-10 |
| 架构 | “你review下当前项目的整体的技术框架、代码架构等有哪些需要优化的地方。（可以派出大量agent去探查，发现的问题回报后你进行复合与分组排序…）” | media-glance，2026-11-11 |
| 架构复扫 | “上一波我们做了架构优化。你再派发大量子agent确认下，你自己review是否还有收益明显的待优化点。” | x-media-saver，2026-11-10 |
| 文档 | “当前项目的文档架构，你梳理下，看是否有需要优化的地方。因为文档较多，你可以排大量子agent分别探查。尤其是那些单个文档过大、职责不清的场景。给我建议优化方案——…让未来的AI…渐进式发现需要的信息…以及持续自动维护这套文档架构。” | media-glance 与 bangou，2026-11-11 |
| 日志 | “你review下当前项目的日志是否合理，例如缺失、冗余等。可以派出大量子agent来探查，你来汇总和裁决。” | 三个项目，2026-11-11 |
| 票据自审 | “你自己review下，重点是：大票、自闭环、依赖关系。”“有问题就优化，没问题就直接建票” | 三个项目 |

保留了“按模块切片派子 agent、主 agent 汇总复核裁决”和文档主题的“渐进式发现”目标。“按必要性排序”“分组排序”“收益明显”是相对判断，改为逐条规则判定；不给子 agent 定条数，写明“没有命中也是合格结论”（x-media-saver 的复扫这样写过，结论是没有切片需要再重构）；“持续自动维护”对应新增检查机制，受文档主题修复约束限制。

## 关键决策

### 流程形态

- **只停一次，停在建 spec 之前**：依据见来源表。带“不要问我”时连这一次也跳过；用户十月用 `/goal` 以同样的授权跑过四轮架构票，可行。跳过停顿时，两个原本要问用户的产品决定取“不做”的一侧：项目没有日志时不引入；修复方案与 ADR 冲突的命中项不进 spec。测试 seam 在停顿时提议，所以停顿要按 `spec.md` 的 seam 规则提。
- **一个 skill 带主题参数**：三个主题只在调研、入选规则、修复约束和验证方式上不同，spec、拆票、实施、合并完全相同。`SKILL.md` 放编排与三个主题共用的部分，主题差异放 `references/topic-*.md`，各阶段做法放其余参考文件；调研之后的阶段都同时读主题文件。
- **不做一次跑完全部主题的入口**：架构改完后文档与日志的调研结论就过期，只能串行，每轮 1～4.5 小时；一轮文档优化就有 19～25 张票（bangou 那轮改了 102 个文件），连跑后要审的量太大，前一轮的偏差会被后一轮当成事实。
- **日志也走完整流水线**：bangou 与 x-media-saver 的日志优化当时是调研后直接修的。用户 2026-11-13 决定统一走流水线：结构一致，建票留痕。代价是小改动也要走完 spec 和拆票。
- **前提不满足直接终止**：缺 Beads 或 `gate-core`、`gate-full` 契约时报告并终止，不提供退路；三个来源项目都由 `setup-project` 初始化，退路没有使用场景（用户 2026-11-13 确认）。新一轮还要求工作树干净且在默认分支，集成分支放在自己的 worktree 里，主工作树不切分支。

### 内化上游

- **内化内容，不包装**：`to-spec`、`to-tickets`、`implement-spec`、`improve-codebase-architecture` 带 `disable-model-invocation: true`，模型无法调用；按插件路径读正文则路径随版本变化，且正文含本 skill 要去掉的人工确认。改写的参考文件注明出处。
- **`improve-codebase-architecture` 只取调研动作**：用户此前手工执行时嫌它要生成 HTML 报告、过重而没用。它的三档强度标签违反“绝对”，“自由探索、记下摩擦”违反“封闭”，所以只保留调研动作，摩擦提问改写成规则表。上游“摩擦足够大才提出重开 ADR”也是相对判断，改为与 ADR 冲突的命中项在停顿里交用户决定。
- **seam 只确认一次**：上游 `to-spec` 与 `tdd` 都在写测试前找用户确认 seam。这里 seam 在唯一的停顿里确认，`spec.md` 与实现子 agent 的简报写明 spec“测试决定”里的 seam 即已确认的 seam。
- **spec 模板**保留上游七节，用户故事从“越多越好”改为每处命中至少一条；新增“调研结果”（逐条报数与未命中的候选）和“代用户做出的假设”。
- 上游 `to-tickets` 的本地文件票据模板、`implement-spec` 的草稿 PR 没带过来：前提已限定 Beads，且本 skill 不推送。

### 状态与编排

- **状态落在票据里**：会话出现过 API 故障、屏幕锁定、上下文压缩三类中断。spec 与票据进 tracker，第一步按票据状态判断阶段，带 spec 编号重新调用即可续跑；用户原先“建完票 `/clear` 再实施”的做法也仍可用。spec 靠标签 `optimize-<主题>` 识别，“读上一轮未命中的候选”、续跑时取主题、热区排除历轮优化票都依赖它。
- **子票在合入集成分支时关闭**，不像上游留到最后统一关，否则中断后无法从票据得知前沿。spec 在合入默认分支后才关。收尾各步的进度记在 spec 评论里。
- **主 agent 只编排**：调研分片给子 agent，每张票一个 worktree 子 agent，合并、review、修复各一个；主 agent 不写产品代码，上下文只留结论。没有子 agent 的 harness 上按同样步骤顺序执行。
- **票据自审交给没看过拆票过程的子 agent**：自审每轮都改票，必须保留；原先同一会话自己审自己。草稿写在仓库之外的临时文件，自审通过后才建票。
- **阶段出口用命令验证**：依赖无环、门禁取退出码（出现过合并子 agent 未检查退出码）、收尾时 worktree 与分支只剩主工作树和既有分支、票据全部关闭，输出写进报告。
- **阻塞只有三类**：仓库事实矛盾且无法判断、权限被拒、桌面会话锁定。权限被拒不得换路径绕过（出现过子 agent 改用 `uv tool install` 绕过拒绝）；锁屏立即失败，不等待（media-glance 曾空等约 9 小时）。
- **合并与清理是流程的一部分，推送不是**：合并、关票、清理 worktree 与分支每次都是同一句指令。
- **报告格式固定**：模型每轮都自发列出代用户的决定、偏离、未验证项等，固定下来便于对照。

### 入选规则

用户 2026-11-13 确认了判定框架、三张规则表与共用规则。规则只看仓库当前内容，不以历史上哪些候选被接受来校准：用户说明自己当时的 review 也不够仔细，不能作为标准。

- **为什么要封闭、绝对、幂等**：media-glance 3 天内 4 次架构扫描每次都报出 4～5 条新的 Strong，用户质疑后模型承认那只是批次内的相对排序；x-media-saver 同一天两次扫描各报出 7～14 条。幂等不成立说明上次漏扫，算本 skill 的缺陷。表外观察只在报告里列成建议清单，同一类观察多次出现时再考虑加规则。零命中以“无需优化”结束，逐条报数让它可以核对。
- **共用规则放在 `SKILL.md`**，调研子 agent 的简报骨架也在那里，主题文件只给切片方式、补充指令和每条规则的“证据”列。原先三个主题文件各放一份共用规则与整段简报，改一处要同改三处。
- **证据由主 agent 复核才算数**：子 agent 的结论在来源会话里被代码推翻过至少两次。
- **“不要问我”不放宽规则**：media-glance 有两条被降级的候选在 `/goal` 授权下照样实现了。
- **B 类只在热区入选**：来自上游的“按提交热点定范围”。去掉这个条件，冷模块里会一直有 B 类命中可修。B4 的阈值取 pylint、SwiftLint、Sonar 的默认上限。
- **文档主题**：三个来源项目的 D1、D4 都已有 `docs-check`，多数时候会以“无需优化”结束。“模拟任务的读取成本”违反幂等（要抽样取任务），只作改造前后的度量。
- **日志主题**：三个来源项目的日志调用点在 18～170 处，可以穷举。media-glance 完全没有日志，因此“是否引入日志”作为产品决定放进停顿。

### 修复约束与验证方式

- **A1 整簇修完**：x-media-saver 的批次对称问题被四轮反复报出，原因是每次只改了孪生的一侧。
- **方案自检**：修完不能长出新的命中，所以目标结构过同一张规则表。
- **文档的修复手段是搬动和重组**：media-glance 的 `sources` 唯一归属等三项新检查上线次日就被删掉，所以新增检查有命中数与机械性的门槛。
- **验证方式按主题分开**：架构每票用 `tdd`，集成分支跑无筛选 `gate-full`。文档只跑 `docs-check`（用户在 media-glance 手动要求过）；本轮改了检查脚本等代码时改跑 `gate-full`。日志不照搬 `tdd`：逐条测日志输出正是 `prune-tests` 会删的那类，只在统一出口留少量测试，其余由 review 核对；门禁与架构相同。
- **主题文件优先于目标项目的 `testing.md`**：模板的 implement-spec 覆盖规则要求最终跑无筛选的完整门禁，文档主题因此要以主题文件为准。
- **收尾顺序**：review → `docs-audit` diff 模式（仅 arch、docs）→ 最终门禁 → 合入默认分支 → 关 spec → 清理 → 出口检查。`docs-audit` 可能改文档，所以排在门禁之前。
- **只允许用户调用**（2026-11-24）：设 `disable-model-invocation: true`，description 不再常驻上下文，只作给人看的一行摘要；一次运行要停下问一次、跨多张票，只会由用户主动发起，没有其他 skill 调用本 skill。

## 与 prune-tests、docs-audit 的分工

两者流程短、判断标准固定、不需要 spec 与拆票，并入只会变慢，还会让一个 skill 里并存两套流程。

| | 本 skill | prune-tests | docs-audit |
| --- | --- | --- | --- |
| 回答的问题 | 结构是否合理，哪些值得改 | 哪些测试该删 | 正文与代码是否一致 |
| 判断依据 | 封闭规则表 | skill 内固定的保留标准 | 代码事实，逐条可证伪 |
| 耗时 | 1～4.5 小时 | 15～27 分钟，两次运行均零干预 | 短，适合定期跑 |

衔接：架构主题的测试精简单独成票，按 `prune-tests` 的规则做（bangou 的一轮运行已自发这样做）；arch 与 docs 收尾跑 `docs-audit` 的 diff 模式；文档调研发现正文与代码不符时建议运行 `/docs-audit`；`prune-tests` 末尾建一张已关闭的留痕票，记在它自己的 design.md。

## 待验收

只核对过格式、路径与 Beads 命令是否存在（`bd dep cycles`、`bd ready`、`bd create --labels/--parent`、`bd list --label/--parent`，bd 1.3.4）。下一步：在一个目标项目上真实运行一个主题，重点核对：

- 三张规则表：同一份代码连扫两次结果是否一致；D2 的“源码范围互不相交”在没有 `covers` 的页面上能否判定；B4 的“互不引用的簇”子 agent 能否画出。
- 热区：提交信息是否带票号、能否可靠剔除优化提交；`bd list --parent` 是否列出已关闭的子票，子票是否继承 `optimize-<主题>` 标签。
- 收尾的 `docs-audit` diff 模式（抽样模式已于 2026-11-13 在三个项目跑通，diff 模式未经真实运行）。
- 调研到实施放在同一会话，上下文是否够用；原先各阶段之间有 `/clear`，`/goal` 运行出现过三次上下文摘要。
- 日志主题“只在统一出口留少量测试”能否防止回退。
- 续跑：在拆票后、实施中途、收尾中途各中断一次，带 spec 编号调用能否从正确的步骤接上。
- 实现子 agent 在 worktree 里调用 `tdd` 时是否仍会停下来确认 seam。
- 没有子 agent 的 harness 上顺序执行时，自审改由主会话重读能否仍起到独立复核的作用。
- 2026-11-23 的精简（共用规则与简报骨架移入 `SKILL.md`、证据要求并入规则表、seam 规则在停顿时引用）未经真实运行。
- 是否像 `setup-project` 那样加 headless 的真实 agent 验收用例未定。
