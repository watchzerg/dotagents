# optimize 设计说明

`skills/optimize` 尚未实现，本文是动手前的设计结论。实现和后续维护前先读本文。记录目标、关键决策、与其他 skill 的耦合和待验收项，只写代码与 git 历史看不出的意图。

## 目标与边界

把“调研 → spec → 拆票 → 实施 → 合并清理”这条项目优化流水线合成一次调用，人工确认从每轮 5～6 次减到 1 次。一条流水线带三个主题：

- `/optimize arch`：框架结构与代码分层。
- `/optimize docs`：文档结构，即单页过大、职责不清、难以按需发现。
- `/optimize logs`：日志缺失与冗余。

不带主题时列出可选项。带 spec 编号调用时续跑。

不做的事：

- 不做功能开发。功能的 spec 需要逐项追问产品决策，不能压成一次确认。
- 不合并 `prune-tests` 与 `docs-audit`，理由见关键决策。
- 不做“一次跑完全部主题”的入口，理由见关键决策。
- 不推送。`git push` 留给用户。

## 来源

2026-11-13 读取了 bangou、media-glance、x-media-saver 三个项目 2026-10-12 至 11-12 的会话，统计用户在各确认点的实际回答。数字来自子 agent 的汇总，没有逐条复核原始会话。

| 确认点 | 用户的实际回答 | 处理 |
| --- | --- | --- |
| to-spec 的 seam 确认 | 约 15 次，几乎全是确认或选推荐项；模型每次都提议沿用现有 seam | 并入唯一的一次确认 |
| to-tickets 的拆票确认 | 从不回答问题，每次贴同一句“自己 review 大票、自闭环、依赖” | 改为固定步骤 |
| 票据自审 | 核实过的每一轮都改了票（20→10、18→22、20→25 等） | 保留，交给独立子 agent |
| implement-spec 中途 | 基本零输入，连续运行 50～110 分钟 | 不变 |
| 结尾的待裁决项 | 全部是“按你的建议处理” | 默认按推荐，报告列出 |
| 合并与清理 | 每次同一句话 | 写进流程 |
| 调研报告之后、建 spec 之前 | 范围取舍与只有用户知道的事实，集中在这里 | 保留这一次 |

最后一行的实例：“日志先不加”“全部三档”“我从来没决策过不写日志”；NAS 暂时无法挂载所以把一张票拆出去、旧部署已切换、某个库可丢弃。

## 关键决策

- **只停一次，停在建 spec 之前**：调研结束后把范围建议、测试 seam、需要用户提供的事实一次问完，之后运行到结束。依据见来源表。调用时带“不要问我”则连这一次也跳过：按推荐执行，所做假设记进 spec。用户十月用 `/goal` 以同样的授权跑过四轮架构票，可行。
- **一个 skill 带主题参数，不做三个 skill**：三个主题只在调研指令、入选门槛和验证方式上不同，spec、拆票、实施、合并完全相同。`SKILL.md` 只写编排与停止规则，各主题和各阶段的做法放 `references/` 按需读取。
- **不做一次跑完全部主题的入口**：架构改完后，文档与日志的调研结论就过期，只能串行，每轮 1～4.5 小时；一轮文档优化就有 19～25 张票（bangou 那轮改了 102 个文件），连跑后一次要审的量太大，前一轮的偏差会被后一轮当成事实。有了本 skill，全做一遍只是依次敲几条命令。
- **日志也走完整流水线**：bangou 与 x-media-saver 的日志优化当时是调研后直接修的。用户 2026-11-13 决定统一走流水线：三个主题结构一致，建票还能留痕。代价是小改动也要走完 spec 和拆票。
- **内化上游四个 skill 的内容，不包装**：`to-spec`、`to-tickets`、`implement-spec`、`improve-codebase-architecture` 带 `disable-model-invocation: true`，模型无法调用；按插件路径读它们的正文则路径随版本变化，且正文包含本 skill 要去掉的人工确认。
  - 前三份合计约 11 KB。保留 spec 模板、纵向切片规则与大范围重构的先扩后收例外、票据模板、实施编排，按 Beads 与 `gate-core`、`gate-full` 改写。
  - `improve-codebase-architecture` 是架构主题调研的基础。用户此前手工执行时因它要生成 HTML 报告、过重而没有用；内化后不生成 HTML，产出改为按客观规则判定的待优化清单，随后不经干预一次修完。用户 2026-11-13 确认。
  - 改写的参考文件注明出处；内化的版本与升级后的吸收步骤见“上游基线”。
  - `tdd` 与 `code-review` 可被模型调用，继续引用。
- **前提不满足直接终止**：目标项目没有 Beads 或没有 just 契约（`gate-core`、`gate-full`）时，第一步就报告缺什么并终止，不提供退路。三个来源项目都是 `setup-project` 初始化的，退路没有使用场景。用户 2026-11-13 确认。
- **票据自审交给没看过拆票过程的子 agent**：自审每轮都改票，必须保留。原先由同一会话自己审自己；改为新子 agent 只拿 spec 与票据草稿，按大票、自闭环、票间依赖三项审。
- **各主题的验证方式分开写**：
  - 架构：每票用 `tdd`，集成分支跑一次无筛选的 `gate-full`。
  - 文档：跑 `docs-check`，不跑 `gate-full`。用户在 media-glance 手动要求过。
  - 日志：不照搬 `tdd`。为日志输出逐条写测试正是 `prune-tests` 会删的那类；只在日志的统一出口留少量测试，其余由 review 核对。
- **入选门槛写成客观标准**：media-glance 3 天内 4 次架构扫描每次都报出 4～5 条新的 Strong，用户质疑后模型承认那只是批次内的相对排序；x-media-saver 同一天两次扫描各报出 7～14 条。各主题的参考文件给出封闭的规则表，零命中时以“无需优化”结束，不为了产出而建 spec。框架与规则见“入选规则”。
- **状态落在票据里，第一步判断阶段**：spec 与票据进 tracker，每个阶段从票据读输入。skill 的第一步固定为根据票据状态判断当前阶段，因此带 spec 编号重新调用即可续跑。会话里出现过三类中断：API 故障、屏幕锁定、上下文压缩。用户原先“建完票 `/clear` 再实施”的做法也因此仍然可用。
- **主 agent 只编排**：调研分发给子 agent 后由主 agent 汇总裁决；每张票一个 worktree 子 agent；合并、review、修复各一个。主 agent 不写产品代码，上下文只留结论。
- **阶段出口用命令验证**：票据依赖无环；门禁检查退出码（出现过合并子 agent 未检查退出码）；收尾时 `git worktree list` 与 `git branch` 只剩 main，票据全部关闭。命令输出写进报告。
- **阻塞的定义写明**：只有三类情况停下：仓库事实互相矛盾且无法判断以谁为准、权限被拒、桌面会话锁定。权限被拒不得换路径绕过（出现过子 agent 改用 `uv tool install` 绕过拒绝）。屏幕锁定立即失败并报告，不等待（media-glance 曾空等约 9 小时）。其余一律按推荐执行并记入报告。
- **合并与清理是流程的一部分，推送不是**：合并进 main、关票、清理 worktree 与分支每次都是同一句指令，写进流程。用户每次手动 `git push`，保持不变。
- **报告格式固定**：代用户做出的决定、与 spec 的偏离、未验证项、遗留票据、出口检查的命令输出、表外建议。会话里模型每轮都自发列出前几项，固定下来便于对照。表外建议是调研中不属于任何规则的观察，只列简短清单，不建票、不修改。

## 入选规则

用户 2026-11-13 确认了判定框架、三个主题的规则表与共用规则。实现时规则表分别写进 `references/topic-arch.md`、`topic-docs.md`、`topic-logs.md`。

### 判定框架

规则只看代码本身，不以历史上哪些候选被接受来校准。用户说明当时自己的 review 也不够仔细，不能作为标准。规则要满足三个性质：

- **绝对**：每条规则对一处代码只有命中或未命中。不做批次内排序，不给子 agent 定条数。
- **幂等**：代码没变，再扫一遍结果为空。不为空说明上次漏扫，算本 skill 的缺陷。
- **封闭**：规则是一张有限的表。表外的观察不进 spec，在运行结束的报告里列成一个简短的建议清单，由用户决定是否另行处理。同一类观察多次出现时再考虑加规则。

上游 `improve-codebase-architecture` 的三档强度标签违反“绝对”，“自由探索、记下摩擦”违反“封闭”，所以内化时只保留调研动作，把它的摩擦提问改写成下面的规则。

零命中时以“无需优化”结束，不建 spec。调研报告逐条规则写“命中 n 处”或“未命中”，使“无需优化”可以核对。

三个主题共用的规则：

- 每处命中附可复核的证据（`文件:行号`、实测数字或可重跑的命令），主 agent 复核后才算数。子 agent 的结论在来源会话里被代码推翻过至少两次。
- 调研顺带发现的行为缺陷单独建票，不混进结构 spec，在那一次停顿时列出，由用户决定是否一起做。
- “不要问我”模式不放宽规则，未命中的不会因为授权而被实现。media-glance 有两条被降级的候选在 `/goal` 授权下照样实现了。
- 调研先读同主题上一轮 spec 的未命中清单，证据没变的不重提。

### 架构规则表

A 类是结构性缺陷，现在就有害：全仓库扫，冷热模块都入选。

| 规则 | 命中判定 | 依据 |
| --- | --- | --- |
| A1 规则重复 | 同一条业务规则（判定、计算、状态迁移、校验、调用顺序）有 3 处以上实现；或 2 处且行为已不一致。判别方法：能用一句领域语言说出这条规则，且改规则时必须同改这几处 | 单一事实来源；三次法则 |
| A2 状态多头写入 | 一份持久或共享状态被 2 个以上模块直接写，绕过它的所有者，或没有所有者 | 封装；单一写入者 |
| A3 依赖方向错误 | 模块间循环依赖；或下层依赖上层，违反项目文档写明的分层 | 无环依赖；依赖指向稳定方 |
| A4 死代码 | 生产路径零引用的模块、函数、参数；只为测试存在的生产方法 | YAGNI |
| A5 违反成文不变量 | 项目的 ADR 或架构文档写明了约束，代码不遵守 | 文档与代码一致 |

B 类是结构性摩擦，下次改动时才付出代价：只在近期在变的区域入选，即涉及文件近 30 天有 3 次以上提交，不计历轮优化票自己的提交。这个条件来自上游的“按提交热点定范围”；去掉它，冷模块里会一直有 B 类命中可修。

| 规则 | 命中判定 | 依据 |
| --- | --- | --- |
| B1 浅模块 | 过半公开成员是纯转发，不增加行为、不变量或策略；删除测试的结果是复杂度消失 | 深模块 |
| B2 假 seam | 接口只有一个适配器，没有东西跨它变化。生产与测试各一个算两个 | 上游“一个适配器是假设，两个才是真的” |
| B3 测试越过接口 | 纯计算或可本地替身的逻辑只能通过真实 I/O 或 UI 测到；或同一段装配代码被 3 个以上测试套件各抄一份 | 接口即测试面 |
| B4 低内聚的大单元 | 文件超过 1000 行且其中的定义能分成 2 组以上互不引用的簇；或函数超过 100 行且圈复杂度超过 15。声明式的装配和表不算 | 高内聚；数字取 pylint、SwiftLint、Sonar 的默认上限 |

不算命中：两段代码相似但表达的是两条恰好相同的规则（不会一起改）；两处未分叉的重复；改名、挪位置、换风格；为将来可能的变化加抽象。

### 文档规则表

范围是当前正文页，不含调研文档、ADR 和生成的文件。

| 规则 | 命中判定 | 依据 |
| --- | --- | --- |
| D1 超预算 | 页面或段落超过项目 `docs-check` 的预算；项目没设预算时用单页 16 KB、单行 1 KB | agent 按页读取，页面大小就是读取成本 |
| D2 多职责页 | 一页里有 2 个以上章节，各自对应的源码范围互不相交，且读者任务不同 | 一页回答一个问题；与 B4 同构 |
| D3 事实重复 | 同一条规范性事实（数值、顺序、规则）在 3 页以上完整陈述；或 2 页且已互相矛盾。索引里带链接的一句话摘要不算 | 单一事实来源；与 A1 同构 |
| D4 不可达 | 当前正文页无法从 INDEX 沿链接到达 | 渐进式发现 |
| D5 路由无判据 | INDEX 条目没有写明什么时候读这页，要打开页面才能判断是否相关 | 渐进式发现 |
| D6 正文依赖历史材料 | 当前正文页的规范性内容要跳到调研文档或变更叙述里才能读全 | 现状与历史分离 |

- 项目的 `docs-check` 已机械覆盖某条规则时，那条直接取检查结果，不再人工扫。三个来源项目的 D1、D4 都已有检查，多数时候本主题会以“无需优化”结束。
- “模拟任务的读取成本”不作规则：它要抽样取任务，两次扫描结果可能不同，违反幂等。只作为改造前后的度量写进报告。
- 正文与代码不符的转 `/docs-audit`。

### 日志规则表

全仓库扫。三个来源项目的日志调用点在 18～170 处，可以穷举。

| 规则 | 命中判定 | 依据 |
| --- | --- | --- |
| L1 失败不可见 | 错误路径既不记日志、也不提示用户、也不向上抛 | 不吞错 |
| L2 失败无法定位 | 缺异常类型或堆栈，缺定位对象的路径或 ID，跨进程缺关联 ID，或字段被静默丢弃 | 日志要能回答哪个对象、为什么 |
| L3 不可逆操作无记录 | 删除、移动、覆盖没有记下对象与原因 | 审计 |
| L4 进程级失败不进日志 | 未捕获异常、启动失败 | 同 L1 |
| L5 空转噪声 | 空闲或轮询时周期性产生、不携带状态变化的行 | 信噪比 |
| L6 重复 | 同一事件的一次发生写出 2 行，或写到 2 个出口 | 一个事件一条记录 |
| L7 故障刷屏 | 故障期间同一错误按固定间隔无限重复 | 信噪比 |
| L8 级别错误 | 预期结果记成 WARNING 或 ERROR；真实失败记成 INFO 或更低 | 级别即告警语义 |
| L9 事件名冲突 | 两个事件同名，或一个事件两种拼写 | 可检索 |
| L10 敏感数据 | 日志里出现密钥、令牌、Cookie、口令 | 安全基线 |

- L1～L4 的每处命中写出排障场景（“X 失败时无法知道 Y”）；L5～L7 要有实测或按代码间隔算出的数量。
- 不算命中：界面已完整展示的失败、逐项成功记录、可配置日志级别、统一命名风格、没有排障场景的字段。
- 项目完全没有日志时，是否引入日志是产品决定，放在那一次停顿里问用户。media-glance 是这种情况。

### 修复约束

规则管入选，下面几条管修完不再长出新的命中：

1. **整簇修完**：命中 A1 时所有副本进同一张票，出口用 grep 证明没有残留。x-media-saver 的批次对称问题被四轮反复报出，原因是每次只改了孪生的一侧。
2. **方案自检**：spec 里的目标结构过同一张规则表。合并重复不得造出浅模块或单适配器接口；新增的日志自己要过 L5～L8。
3. **逐条报数**：见判定框架。
4. **文档的修复手段是搬动和重组内容**：新增检查项或 frontmatter 字段，只在某条规则本次命中 3 处以上、检查完全机械、不需要逐页手工维护数据时才做。media-glance 的 `sources` 唯一归属等三项检查上线次日就被删掉。
5. **日志能在统一出口修的不逐点修。**

## 不合并 prune-tests 与 docs-audit

两者流程短、判断标准固定、不需要 spec 与拆票，并入只会变慢，还会让一个 skill 里并存两套流程。

| | 本 skill | prune-tests | docs-audit |
| --- | --- | --- | --- |
| 回答的问题 | 结构是否合理，哪些值得改 | 哪些测试该删 | 正文与代码是否一致 |
| 判断依据 | 设计取舍，要排序选范围 | skill 内固定的保留标准 | 代码事实，逐条可证伪 |
| 耗时 | 1～4.5 小时 | 15～27 分钟，两次运行均零干预 | 短，适合定期跑 |

衔接方式：

- 架构主题里，测试精简由单独的票按 `prune-tests` 的规则做。bangou 的一轮运行已自发这样做。
- 文档与架构主题收尾时，以集成分支的基准跑 `docs-audit` 的 diff 模式，核对被搬动或受影响的页面。
- 文档主题的调研只看结构。发现正文与代码不符时在报告里建议运行 `/docs-audit`，不纳入本次 spec。
- `prune-tests` 末尾加一步：建一张已关闭的票记录前后用例数与保留范围，使四种优化都有票据留痕。这是对 `prune-tests` 的改动，实现时同步更新它的 design.md。
