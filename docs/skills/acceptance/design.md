# acceptance 设计说明

维护 [`skills/acceptance`](../../../skills/acceptance/SKILL.md) 前先读本文。只写代码与 git 历史看不出的意图。

## 目标与边界

让 agent 在用户本机真实环境上按项目行为文档把功能验收一遍：真实启动、逐项操作、同时观察界面、日志、数据与可写目录，偏差就地修复并重跑，直到一次零修复的全量通过，留下报告。定位是 QA 在 staging 上按功能清单手工过一遍的活，不是 e2e 自动化：一次运行不可重复、不进门禁；沉淀的是修复 commit、随修复补的测试和 `docs/research/acceptance/` 下的记录。

不假设目标项目有浏览器、数据库或网络服务：观测通道由项目环境契约声明，CLI、后台任务、桌面应用同样适用。

## 关键决策

- **预期只来自文档，文档权威**：`docs/behaviors/` 优先，退到模块页“当前行为规格”，两处都没有就不验。代码里有而文档没写的列“未覆盖”，否则验收退化成“代码与自己一致”。要改文档才能通过的项一律 DEFERRED 写票，agent 不裁决、不改文档迁就代码。
- **环境契约独占一页，只认精确路径**：启动、停止、就绪、日志、数据查询与重置、可写目录、禁区都来自 `docs/development/local-acceptance.md`。契约原是 `workflow.md` 里的一节、按节名查找，有两个问题：`workflow.md` 是改代码任务的必读页，契约对它们是负担；节名是隐性接口，项目一移就找不到。所以独占一页、不设回退（两个落点在迁移中途无法判断哪份有效）。缺失时起草整页并入唯一一次确认；新建时照同目录页面补元数据并接入索引，否则带生成索引的项目文档检查会红。不让 agent 每次从代码猜环境，因为猜错的代价是对真实环境误操作。
- **验收数据与日常数据分开**：验收会写入、重跑、重置数据，指向日常库等于让 agent 清空或污染真实数据。契约要求指向验收专用数据；只能用日常数据时不给重置命令并列入禁区。
- **只问一次**：清单推导后集中确认一次清单与契约草稿，之后只在硬阻塞停下。清单是整次运行的边界，确认成本低；其余决定（就地修还是写票、重跑范围）都有规则。
- **就地修复的边界与收敛条件**：局部、不改 schema 与公共接口、不涉设计取舍的才就地修，先补失败测试，一处一个 commit；其余写票继续。修复后重跑同来源文件的项；本次有过修复时最后重置、重启、全量零修复重跑一次才算完成，否则“边验边修”会让已通过的项失去意义。
- **`无法观测` 是终态之一**：预期涉及的通道无法观测时不能记 PASS，又不是缺陷，若不设独立状态，这类项永远达不到完成条件。它与 PASS、FIXED、DEFERRED 并列为终态，单独计数进报告。
- **账本在临时目录，报告进项目**：账本是跨轮唯一真相（对话会被压缩），放会话临时目录不污染仓库；报告落 `docs/research/acceptance/`，因为模板已为验收证据留了这个位置，下次运行可对比。
- **与多轮循环的分工**：Claude Code 的 `/goal` 只能由用户输入（skill 无法设定），但 goal 条件可以引用 skill（anthropics/claude-code#58348）。所以 SKILL.md 给出推荐命令，skill 负责流程与判据，循环负责“没跑完别停”。评估器只读 transcript，因此每轮打印以 `验收进行中` 开头的摘要，`验收完成` 只在报告 commit 后打印；这套输出约定对任何循环机制都无害。未采用 skill frontmatter 自带 prompt 型 Stop hook 的自包含路线：goal 可观测、可 `/goal clear`，一跑一小时的活可观测比省一行输入重要。
- **服务脱离 harness 启动**：goal 评估在后台任务未结束时会跳过，用 harness 的后台模式起服务等于没设 goal。所以契约要求启动命令自行后台化，agent 前台调用，修复时按契约反复启停。
- **浏览器用用户自己的 Chrome**：最接近真实使用，复用登录态，能读 console 与 network。首版曾选 Playwright MCP headless（独立实例），用户改为真实浏览器，理由是真实环境与登录态复用更不容易出错。代价是操作真实浏览器与账号，所以 browser.md 写死范围：只访问契约地址、只用自建标签页、不登出、不动其他标签页，禁区由契约声明；原生对话框会阻塞扩展，列为硬阻塞。未连接时不回退：悄悄换成无登录态的独立浏览器会让环境偏离真实使用。只有 harness 没有原生方案时才用 Playwright skill + CLI。总规则在 `global/AGENTS.md` 浏览器测试节，skill 只写验收特有的部分。
- **harness 中立**：用户同时使用多个 harness。SKILL.md 只写能力要求与操作边界，不写工具名；各 harness 的浏览器做法集中在 `references/browser.md` 的映射表，新增 harness 只改这张表。
- **“验收”一词只指本 skill**：setup-project 模板曾把 `gate-full` 通过也叫“完整验收”。划分标准是可重复且结果确定的进 core 或 full，依赖真实账号、真实外部服务或人工判断的归本 skill。
- **暂不设 `disable-model-invocation`**（2026-11-24）：若 `/goal` 由模型读到 `/acceptance` 后经 Skill 工具调用，设了就会失效；待验收项中 `/goal` 的触发方式确认后再定。

## 与 setup-project 的耦合

- 模板提供 `docs/development/local-acceptance.md`（`按需` 待填标记，列出要回答的问题），由 `workflow.md` 开头的指路句与 `docs/INDEX.md` 入链。已有项目缺这一页时由 setup-project 补缺，或由本 skill 起草。
- `docs/agents/documentation.md` 的行为规格模板让 behaviors 与模块页用户可见部分按“场景与前提 → 操作与可观察结果 → 边界与错误情况”写，清单可逐段映射。模板只写功能描述，不写测试步骤。
- 报告登记在 `docs/research/INDEX.md` 的“验收记录”表。

## 待验收

- 尚未在任何真实项目上跑过。首个目标：有 web 界面与数据库的项目各一次 all 模式、一次 topic 模式；再跑一个纯 CLI 项目验证“不假设浏览器与数据库”的措辞够用。
- `/goal /acceptance 直到打印"验收完成"，最多 80 轮` 能否让首轮正确触发 skill、评估器是否按 `验收完成` 判定；最短形式 `/goal /acceptance` 是否可用（评估器可能拿不到判据而首轮就判完成）。
- 阶段 1 的结构化提问（Claude Code 的 AskUserQuestion）在 goal 激活期间是否会被评估器判为失败。
- 契约起草的证据来源是否够用，取决于真实项目的 `mise.toml` 与 README 质量。
- 除 Claude Code 外，其他 harness 的浏览器做法未填入映射表，也未在其他 harness 上运行过。
- Chrome 扩展在一小时以上的运行里是否稳定（断连、标签页被误关）。
- `无法观测` 作为终态是本轮精简时为消除完成条件的矛盾新增的，未经真实运行。
