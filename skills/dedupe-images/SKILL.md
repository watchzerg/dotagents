# 图片库去重

脚本 `scripts/dedupe_images.py` 负责扫描、出材料和执行，模型负责抽查和判断案例。文件的移走、移动、改名只经 `clean --apply`、`apply`、`apply-decisions` 完成：移走一律进系统回收站，执行前脚本按 SHA-256 复核被移走的内容在保留处仍有一份；计划 JSON 只读。需要 `python3` 3.14+（只用标准库），支持 macOS 15+ 与 Linux。下文 `<脚本>` 指该脚本的完整路径；`<临时目录>` 用会话临时目录，计划与决策文件不写进图片库。

## 步骤

1. **确定总目录**：取用户给出的路径；没给就问。
2. **清理杂项**：运行 `python3 <脚本> clean "<总目录>"`，列出残缺下载、广告链接、元数据、文件夹图标、看图软件与系统残留（不含 txt）。清单里没有作品本体就加 `--apply` 执行，不用问用户。向用户转述各类数量、输出里“移走后作品会缺这些页”的残缺文件，以及不处理的其余非图片文件类型。
3. **生成计划**（不改动文件，大库可能要几分钟）：

   ```sh
   python3 <脚本> plan "<总目录>" --out "<临时目录>/plan.json"
   ```

   向用户转述摘要：自动处理部分的数量与体积、案例数。
4. **抽查自动部分**：运行 `python3 <脚本> show "<临时目录>/plan.json" --sample 5`，逐条核对：
   - 移走后编号不出现空缺（只剩 `01…09` 而 `10…` 被移走且没有对应保留项就是空缺）；
   - 留下的文件名、目录名不比移走的差，目录级的保留目录是更完整的那份；
   - “移走超过一半图片的目录”逐个合理。

   有疑问就读计划 JSON（`dir_removals[]`，`dirs[].groups[]` 的 `keep`、`remove`、`rename_to`、`match`）或列目录。全部合理就直接进入下一步；有不合理的就停下，把问题和样本报告用户：这说明脚本规则有漏洞，要修脚本。
5. **执行自动部分**：运行 `python3 <脚本> apply "<临时目录>/plan.json"`，如实转述数量、体积、跳过项和失败项（退出码 1 为有失败项；2 为计划不可用或平台不支持，未改动文件）。文件级去重后常有目录变得内容相同，所以回到第 3 步重新 plan，自动部分仍有内容就再走第 4、5 步，直到自动部分为空；用最后这份计划判断案例。
6. **判断案例**：用 `show "<临时目录>/plan.json" [编号 ...]` 取材料（不给编号输出全部），按[案例判断规则](#案例判断规则)给每个案例写出决策。`show` 中用「」括起的路径首尾带空白，写进决策时保留这些空白。案例几十个以上时按编号分批交子 agent 并行判断：每个子 agent 拿到编号与“案例判断规则”“决策文件”两节，返回各案例的 `actions` 和一句理由；主 agent 汇总并抽看理由。
7. **试跑并请用户确认**：把全部决策写进 `<临时目录>/decisions.json`，运行 `python3 <脚本> apply-decisions "<临时目录>/decisions.json" --check`（不改动文件，按顺序模拟各案例，有跳过项时退出码为 1）。按跳过原因修正：保留处缺的文件补 `move` 过去，与前面案例冲突的合并成一个案例或改判 `keep`，直到没有跳过项。然后给用户列表，每个案例一行：编号、涉及的目录或文件、建议（移走、移动什么、保留）和一句理由，看过图的注明。用户可以逐条改；未经用户确认不执行。
8. **执行决策**：按用户确认的结果更新决策文件，运行 `python3 <脚本> apply-decisions "<临时目录>/decisions.json"`，如实转述执行数、跳过的案例及原因。合并与移动之后常出现新的包含关系，所以回到第 3 步重新 plan：有自动部分或新案例照常处理，只剩已判定 `keep` 的案例时结束。

判断或执行前目录又被改动过、或距 plan 已久，先重新 plan。

## 案例判断规则

按顺序取第一条适用的：

- **作品内部结构的重复**：同一部作品里有意重复放置的内容，如每集都附的人物介绍（后面集数的更全，前面的成了子集）、外层当缩略图的封面在下层正文里另有一份：`keep`，不必让用户逐条确认，在表中合并为一行说明。
- **合集恰好由单章拼成**（材料里有“合集 … 恰好由 N 个单章拼成”）：移走合集、保留单章。单章都在合集目录下时，对合集目录 `trash_matching`（`keep` 列出单章）；都在合集之外的同一父目录下时 `trash` 合集，`keep` 列出各单章；分散在几处时把各单章 `move` 进合集目录，再对合集目录 `trash_matching`（`keep` 列出单章原路径），合集目录就成了单章的父目录。某个单章移出会拆散它所在的另一个合集时，整案 `keep`。材料里列出的重复单章按下面的规则另行判断。
- **独立作品被画师杂图包包含**（Patreon 包、Pixiv 或 Fanbox 合集、`Art` 这类汇总目录）：保留独立作品，对杂图包 `trash_matching`（`keep` 为独立作品），杂图包其余内容不动。单行本、系列合集不算杂图包（删页会拆坏书）；两边都是画师合集、分不出哪个是独立作品时 `keep`。重叠图片移走后，独立作品常在重新 plan 时与下一个包含它的杂图包配对：接着按本条判断；若新的包含方是编号连续的单个作品或图集（如 `The_Other_Side_187…196`），删掉会使编号中断，`keep`。
- **其他目录案例**（`=` 内容相同，`⊂` 子集）：看命名、编号范围与缺号、目录名、所在合集结构，保留更完整、更规范的一方：按章节分子目录的优于全部平铺的，带作者标签、多出版本（无字版、外传）的优先，已有整理好的总合集时把散落版本并进去。
  - 一方只是另一方的不完整副本：移走它。
  - 两个合集大部分相同：合并，把一方独有的子目录或零星图片 `move` 进另一方对应位置，再整体 `trash`。
  - 一方命名好（带话数、封面等信息）、另一方是流水号但图片更全：保留命名好的一方，把只在另一方的图片带 `name` 移过来再整体 `trash`。新名字取它在原目录里前一张已有图片在保留方的文件名主干，加 `_` 和原编号（`863_999.png` 之后的 `00000864.png` 改为 `863_999_864.png`；原目录里排第一的用 `0_` 开头，如 `01_smile2.jpg` 改为 `0_smile2.jpg`），这样按文件名排序时仍在原来的位置。用 `_` 是因为它排在 `.` 之后；`-`、`+`、空格排在 `.` 之前，会跑到前一张前面。
  - 材料标“含子目录”的配对只比较了这一层的图片，下级目录常有别处没有的版本：对这一层用 `trash_matching`。
  - 单章与合集、旧版与新版各有用途，同一份几张图分属两个作品集，或独有的图归不到具体章节：`keep`。
- **文件案例**（同名同体积、内容不同）：先看材料里的损坏特征与不同字节的位置；仍判断不了时打开两张图对比，每次运行最多看 10 个案例。画面不同就 `keep`。

## 决策文件

```json
{
  "root": "<总目录的绝对路径>",
  "actions": [
    {"case": "c012", "op": "move", "src": "A合集/独有的一话", "dest": "B合集"},
    {"case": "c012", "op": "trash", "path": "A合集", "keep": ["B合集"]},
    {"case": "c013", "op": "move", "src": "流水号版/00000864.png", "dest": "命名版", "name": "863_999_864.png"},
    {"case": "c013", "op": "trash", "path": "流水号版", "keep": ["命名版"]},
    {"case": "c014", "op": "trash_matching", "path": "画师杂图包", "keep": ["独立作品"]},
    {"case": "c015", "op": "keep"}
  ]
}
```

路径相对总目录，按执行前的位置写。

- `move`：把 `src` 移进已存在的目录 `dest`，目标里不能有同名项；可选 `name` 指定移入后的新名字。
- `trash`：`path` 是目录或文件，`keep` 列出它的内容所在的保留路径。
- `trash_matching`：`path` 是目录，只移走它直接包含的、在 `keep` 下有相同内容的文件；`keep` 可以是本案例里将被移动的目录。
- `keep`：不动。

同一案例的操作一起校验：被移走的每个非隐藏文件都要在 `keep` 下（含移进 `keep` 的目录）有 SHA-256 相同的文件，`keep` 不能在被移走的路径里；任一项不满足，整个案例跳过。执行顺序是先移动、再移入回收站、最后删除变空的上级目录。
