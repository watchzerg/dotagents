# 建 spec

改写自 Matt Pocock 的 `to-spec`（MIT 许可，<https://github.com/mattpocock/skills>，插件 `mattpocock-skills` 1.3.1）。原 skill 在这一步向用户确认 seam；这里 seam 已在唯一的那次停顿里确认。

输入是调研报告与用户在停顿时的回答。不再追问：没问到的按推荐决定，记进“代用户做出的假设”。

## seam 规则

- 优先用已有的 seam，新 seam 只在已有的都测不到目标行为时提出。
- 取能测到目标行为的最高一层。
- 全仓库的 seam 越少越好，理想是一个。
- `docs` 主题没有测试 seam，写“由 `docs-check` 验证”。`logs` 主题的 seam 是日志的统一出口。

## 步骤

1. 确定范围：命中项减去用户排除的项。范围之外的命中项记入“范围之外”，保留证据。
2. 为每处命中写目标结构，然后做**方案自检**：目标结构过主题文件的同一张规则表，过不了就改方案。主题文件的其余修复约束同样适用。
3. 按模板写 spec，全文用项目 `GLOSSARY.md` 的词汇，遵守涉及区域的 ADR。
4. 按 `docs/agents/issue-tracker.md` 发布到 tracker：标签 `optimize-<主题>`，另加 `docs/agents/triage-labels.md` 中对应 `ready-for-agent` 的标签。
5. 出口：spec 编号存在，且“调研结果”里每条规则都有一行。

## 模板

```markdown
## 问题陈述

本轮要消除的命中项：每项一行，写规则编号、位置、现在造成的代价。

## 方案

改完之后的结构，按命中项分组。写方案自检的结论：目标结构对规则表逐条未命中。

## 用户故事

编号列表，每处命中至少一条。格式：作为 <维护者、排障者或读文档的 agent>，我希望 <改完后的状态>，以便 <收益>。

## 实现决定

- 要新建或修改的模块，以及它们的接口怎么变
- 所有者、依赖方向、统一出口等架构决定
- 用户在停顿时提供的事实

不写文件路径和代码片段，它们很快过期；位置信息只出现在“调研结果”的证据里。

## 测试决定

- 测试的 seam，以及每个 seam 能测到什么、测不到什么
- 好测试的标准：只验证经接口可观察的行为
- 仓库里可参照的同类测试
- 本主题的验证方式（取自主题文件）

## 调研结果

| 规则 | 结果 | 证据 |
| --- | --- | --- |
| <编号与名称> | 命中 n 处 / 未命中 | `文件:行号`、数字或命令 |

### 未命中的候选

子 agent 报出、主 agent 复核后判为未命中的项：位置、规则、判为未命中的证据。下一轮调研读这一节，证据没变的不重提。

## 代用户做出的假设

“不要问我”模式或停顿时没问到的决定：每项写选择与理由。没有就写“无”。

## 范围之外

本轮不做的命中项及原因；顺带发现的行为缺陷票编号。
```
