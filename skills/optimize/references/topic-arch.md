# 架构主题：框架结构与代码分层

调研做法改写自 Matt Pocock 的 `improve-codebase-architecture`（MIT 许可，<https://github.com/mattpocock/skills>，插件 `mattpocock-skills` 1.3.1）。取其调研动作；候选是否入选改由下面的规则表判定。

## 调研

1. **取词汇。** 调用 Skill `mattpocock-skills:codebase-design`，全程使用其中的 module、interface、depth、seam、adapter、leverage、locality；领域概念用项目 `GLOSSARY.md` 的名称。为命中项设计目标结构时读它的 `DEEPENING.md`，按依赖类别决定 seam 与测试方式。
2. **读约束。** `GLOSSARY.md`、`docs/adr/` 下的 ADR、架构与分层文档。ADR 记下的决定不重新讨论，写明的约束用于判定 A5。
3. **读上一轮。** 取最近一份带 `optimize-arch` 标签的 spec（含已关闭），读其“未命中的候选”。证据没变的不重提。
4. **定热区。** B 类只在热区入选。列出近 30 天有 3 次以上提交的文件，不计历轮优化票自己的提交：

   ```sh
   git log --since='30 days ago' --format= --name-only \
     --invert-grep --grep='<票号 1>' --grep='<票号 2>' \
     | sed '/^$/d' | sort | uniq -c | awk '$1>=3'
   ```

   `--grep` 填历轮优化票的编号：带 `optimize-arch`、`optimize-docs`、`optimize-logs` 标签的全部票据（含已关闭）。没有历轮票时去掉这一行。提交信息不带票号、无法剔除时，在调研报告注明“热区未排除优化提交”。
5. **分片探查。** 按模块把全仓库切片，每片派一个只读子 agent，简报见下。A 类全仓库扫，冷热模块都入选；B 类只看热区文件所在的模块。
6. **汇总裁决。** 主 agent 合并各片结果，跨片的 A1、A2、A3 要合起来看；回到源码复核每处命中的证据，证据不成立的移入“未命中的候选”并写明原因。
7. **处理 ADR 冲突。** 命中项的修复方案与某条 ADR 冲突时，不绕过 ADR：在那次停顿里列出该项与冲突的 ADR，由用户决定是否重开；“不要问我”模式下该项不进 spec，在报告列出。

### 子 agent 简报

把占位换成实际值后下发：

> 梳理 `<切片路径>` 的框架结构与代码分层，逐条按 `<本文件绝对路径>` 的规则表与“不算命中”判定。只读，不改任何文件。先调用 Skill `mattpocock-skills:codebase-design` 取词汇。
>
> - 对每条规则回答“命中 n 处”或“未命中”。没有命中也是合格结论；不排序，不凑条数，不标强弱。
> - B 类只在这些热区文件所在的模块判定：`<热区文件清单>`。
> - 每处命中给出证据：`文件:行号`，加上该规则判定所需的事实。A1 写出那句领域语言的规则和各处实现的位置；A2 列出状态与所有写入方；A3 给出依赖链；A4 给出证明零引用的可重跑命令；A5 给出文档条款与违反它的代码位置；B1 列出公开成员并标出纯转发的；B2 列出接口与它的全部适配器；B3 指出逻辑位置与只能触达它的测试；B4 给出行数、簇的划分或圈复杂度及其测量方式。
> - 疑似浅模块先做删除测试：删掉它，复杂度是消失，还是在调用方重新出现。
> - 行为缺陷（与结构无关的 bug）单独列出，附代码路径。
> - 不属于任何规则的观察放在末尾“表外观察”，每条一行。

## 入选规则

规则只看代码本身。每条规则对一处代码只有命中或未命中；代码没变，再扫一遍结果为空；表外的观察不进 spec。

### 共用规则

- 每处命中附可复核的证据（`文件:行号`、实测数字或可重跑的命令），主 agent 复核后才算数。子 agent 的结论被代码推翻过不止一次。
- 调研顺带发现的行为缺陷单独建票，不混进结构 spec，在那一次停顿时列出，由用户决定是否一起做。
- “不要问我”模式不放宽规则，未命中的不会因为授权而被实现。
- 调研先读同主题上一轮 spec 的未命中清单，证据没变的不重提。

### 架构规则表

A 类是结构性缺陷，现在就有害：全仓库扫，冷热模块都入选。

| 规则 | 命中判定 | 依据 |
| --- | --- | --- |
| A1 规则重复 | 同一条业务规则（判定、计算、状态迁移、校验、调用顺序）有 3 处以上实现；或 2 处且行为已不一致。判别方法：能用一句领域语言说出这条规则，且改规则时必须同改这几处 | 单一事实来源；三次法则 |
| A2 状态多头写入 | 一份持久或共享状态被 2 个以上模块直接写，绕过它的所有者，或没有所有者 | 封装；单一写入者 |
| A3 依赖方向错误 | 模块间循环依赖；或下层依赖上层，违反项目文档写明的分层 | 无环依赖；依赖指向稳定方 |
| A4 死代码 | 生产路径零引用的模块、函数、参数；只为测试存在的生产方法 | YAGNI |
| A5 违反成文不变量 | 项目的 ADR 或架构文档写明了约束，代码不遵守 | 文档与代码一致 |

B 类是结构性摩擦，下次改动时才付出代价：只在近期在变的区域入选，即涉及文件近 30 天有 3 次以上提交，不计历轮优化票自己的提交。去掉这个条件，冷模块里会一直有 B 类命中可修。

| 规则 | 命中判定 | 依据 |
| --- | --- | --- |
| B1 浅模块 | 过半公开成员是纯转发，不增加行为、不变量或策略；删除测试的结果是复杂度消失 | 深模块 |
| B2 假 seam | 接口只有一个适配器，没有东西跨它变化。生产与测试各一个算两个 | 上游“一个适配器是假设，两个才是真的” |
| B3 测试越过接口 | 纯计算或可本地替身的逻辑只能通过真实 I/O 或 UI 测到；或同一段装配代码被 3 个以上测试套件各抄一份 | 接口即测试面 |
| B4 低内聚的大单元 | 文件超过 1000 行且其中的定义能分成 2 组以上互不引用的簇；或函数超过 100 行且圈复杂度超过 15。声明式的装配和表不算 | 高内聚；数字取 pylint、SwiftLint、Sonar 的默认上限 |

不算命中：两段代码相似但表达的是两条恰好相同的规则（不会一起改）；两处未分叉的重复；改名、挪位置、换风格；为将来可能的变化加抽象。

## 修复约束

规则管入选，下面几条管修完不再长出新的命中：

1. **整簇修完**：命中 A1 时所有副本进同一张票，出口用 grep 证明没有残留。只改孪生的一侧，下一轮会再次报出同一处。
2. **方案自检**：spec 里的目标结构过同一张规则表。合并重复不得造出浅模块或单适配器接口。
3. **逐条报数**：调研报告逐条规则写“命中 n 处”或“未命中”，使“无需优化”可以核对。

## 验证方式

- 每张票由实现子 agent 调用 Skill `mattpocock-skills:tdd` 完成，在 spec 写明的 seam 上测试。
- 结构调整使旧测试失去意义时，测试精简单独成票，按 `/prune-tests` 的保留与删除标准处理受影响的测试。
- 每票出口：`just gate-core` 退出码为 0。
- 集成分支：一次无筛选的 `just gate-full`。
- 收尾以集成分支的基准运行 `docs-audit` 的 diff 模式。
