# 日志主题：缺失与冗余

## 调研

1. **穷举调用点。** 用 grep 列出全部日志调用点与统一出口（logger 的配置、封装函数、handler），记下总数。项目完全没有日志时不往下扫：是否引入日志是产品决定，放在那一次停顿里问用户；“不要问我”模式下不引入，在报告写明后结束。
2. **分片探查。** 按模块把全仓库切片，每片一个只读子 agent。简报的主题范围为“日志的缺失与冗余”，本主题补充：
   - 本片的日志调用点：`<清单或 grep 命令>`。
   - L1～L4 查的是“该有而没有”，只看已有调用点查不出来：逐个读本片的错误处理分支（`except`、`catch`、错误回调、返回错误码处）、删除、移动、覆盖操作和进程入口。
3. **汇总。** L6、L9 要跨片合起来看。

## 规则表

| 规则 | 命中判定 | 证据 | 依据 |
| --- | --- | --- | --- |
| L1 失败不可见 | 错误路径既不记日志、也不提示用户、也不向上抛 | 排障场景：“X 失败时无法知道 Y” | 不吞错 |
| L2 失败无法定位 | 缺异常类型或堆栈，缺定位对象的路径或 ID，跨进程缺关联 ID，或字段被静默丢弃 | 同 L1 | 日志要能回答哪个对象、为什么 |
| L3 不可逆操作无记录 | 删除、移动、覆盖没有记下对象与原因 | 同 L1 | 审计 |
| L4 进程级失败不进日志 | 未捕获异常、启动失败 | 同 L1 | 同 L1 |
| L5 空转噪声 | 空闲或轮询时周期性产生、不携带状态变化的行 | 数量：实测，或按代码里的间隔算出每小时多少行并写出算式 | 信噪比 |
| L6 重复 | 同一事件的一次发生写出 2 行，或写到 2 个出口 | 同 L5 | 一个事件一条记录 |
| L7 故障刷屏 | 故障期间同一错误按固定间隔无限重复 | 同 L5 | 信噪比 |
| L8 级别错误 | 预期结果记成 WARNING 或 ERROR；真实失败记成 INFO 或更低 | 该事件是预期结果还是真实失败及依据 | 级别即告警语义 |
| L9 事件名冲突 | 两个事件同名，或一个事件两种拼写 | 冲突的各处 | 可检索 |
| L10 敏感数据 | 日志里出现密钥、令牌、Cookie、口令 | 字段名，不抄录敏感值 | 安全基线 |

不算命中：界面已完整展示的失败、逐项成功记录、可配置日志级别、统一命名风格、没有排障场景的字段。

## 修复约束

1. **方案自检**：spec 里的目标结构过同一张规则表。新增与改动的日志自己要过 L5～L8。
2. **统一出口优先**：能在统一出口修的命中合成一张票在出口修，不按调用点逐个修。

## 验证方式

- 只在日志的统一出口留少量测试，例如去重、限频、字段不丢、未捕获异常进日志，由实现子 agent 调用 `tdd` 完成；统一出口即 spec 的测试 seam。逐个调用点的日志输出不写测试。
- 其余命中由 review 核对：收尾 review 的修复子 agent 逐处对照 spec 的命中清单确认已修，并确认新增与改动的日志过 L5～L8。
- 每票出口：`mise run gate-core`。
- 集成分支门禁：一次无筛选的 `mise run gate-full`。
