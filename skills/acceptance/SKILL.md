# 真实环境验收

对当前工作目录的项目做 QA 式验收：以行为文档为预期，在本机启动真实运行形态，按项目环境契约声明的通道逐项观察，偏差就修，直到一次零修复的全量通过，最后写报告。产出是修复 commit、随修复补的测试和报告。

可选参数 `<topic>`：只验 `docs/behaviors/<topic>.md`（或同名模块页），完成条件随之缩到该主题。只取第一个词作 topic，其余文字忽略。

`references/` 下的文件在链接它的步骤到达时再读。

## 运行方式

一次验收通常持续几十轮。harness 支持用户设定目标、自动多轮推进的循环时（如 Claude Code 的 `/goal`），推荐用户这样启动：

```text
/goal /acceptance 直到打印"验收完成"，最多 80 轮
```

主题模式写 `/goal /acceptance <topic> 直到打印"验收完成"，最多 40 轮`。没有这类循环时直接 `/acceptance`，每次停下由用户说“继续”。

循环的评估器只读对话，所以输出遵守两条约定：

- **停下前**先写账本，再打印一行摘要，固定以 `验收进行中` 开头：

  ```text
  验收进行中：总数 24，PASS 15，FAIL 1，FIXED 2，DEFERRED 1，无法观测 0，剩余 5；本轮修复 1；账本 /path/to/ledger.md
  ```

- `验收完成` 四字只在阶段 5 的最后一行出现，其他任何输出都不连写这四个字。

一轮做到无法继续（硬阻塞、需要提问或阶段完成）才停，不为汇报进度提前停。

## 基本约束

- **环境契约**是唯一的环境依据：被验对象可能是 web 服务、CLI、后台任务、库的示例程序或桌面 app，界面、数据位置与观测方式全部以契约声明为准。契约没声明的通道就是不存在，不猜数据库连接串、不另起浏览器找界面。
- **账本**是跨轮唯一真相：每轮先读账本再行动；对话被压缩后以账本为准。
- 契约声明 web 界面时，浏览器方案的选择（按是否需要用户真实登录态）、连接、标签页与取证按 [references/browser.md](references/browser.md)。

## 阶段 0：前提与输入（只读）

1. 当前目录是 Git 工作区根目录且工作树干净；有未提交改动时停下，让用户先提交或暂存（修复会逐个 commit 到当前分支）。
2. 预期来源：`docs/behaviors/*.md`，其次 `docs/architecture/modules/*.md` 的“当前行为规格”章节。两处都没有可用内容时停下说明“没有可验收的预期”，预期只来自文档。给了 `<topic>` 时只取对应文件；找不到就停下列出可选主题。
3. 环境契约：`docs/development/local-acceptance.md` 整页，只认这个路径，要求见 [references/environment.md](references/environment.md)。文件缺失或仍是 `<待填` 标记时按该文件起草整页，纳入阶段 1 的确认。
4. 观测工具：web 界面按 browser.md 选定浏览器方案并确认可用，写入账本；其他通道逐个确认契约声明的命令可执行。
5. 账本：在会话临时目录（有 scratchpad 用它，否则 `mktemp -d`）建 `ledger.md`，打印路径；格式见 [references/checklist.md](references/checklist.md#账本)。

## 阶段 1：清单与一次确认

1. 按 [references/checklist.md](references/checklist.md) 从预期来源推导验收项。
2. 把清单、契约草稿（如有）、将执行的数据重置动作写入账本，集中提问一次（harness 有结构化提问工具时用它），停下等用户确认或调整。用户调整后更新账本。此后只在硬阻塞时提问。
3. 契约草稿经确认后按 environment.md 写入项目，单独 commit。

## 阶段 2：环境就绪

1. 契约有数据重置命令就执行；没有时账本记“未重置”，断言只用本次运行产生的数据。
2. 用 shell 前台调用契约的启动命令（它自行后台化，见 environment.md），等待契约的就绪条件。不用 harness 自带的后台执行功能：部分 harness 的多轮循环在后台任务未结束时跳过每轮评估。
3. 记录基线：日志文件当前长度、契约数据检查命令的输出、可写目录的文件清单。之后每项证据都相对基线取增量。
4. 有 web 界面时按 browser.md 打开验收专用页面。

## 阶段 3：逐项验收

串行执行。只读的定位与分析可派子 agent，操作环境的动作不并行。每项：

1. 执行操作。
2. 在契约声明的每个通道取证：界面（页面文本或截图、命令输出；web 另读 console 错误与失败的 network 请求）、日志新增行、数据查询结果、可写目录变化、契约给的外部副作用检查。
3. 对照预期，账本写状态并附证据摘要。

判定标准：

- 零输出、零匹配、“没有报错”不算通过。
- 措辞差异按语义判；有实质差异判 FAIL 并写明差在哪。
- 预期涉及的通道无法观测、其余通道都符合时记 `无法观测`，写明哪个通道。
- 预期里没提但观察到的 console 错误或 4xx/5xx 响应记入账本“疑点”，不单凭它判 FAIL。

## 阶段 4：偏差处理

对每个 FAIL 先定位原因，再归入下列一类：

- **文档问题**：文档与代码冲突且该改的是文档（规则不合理、已被后续决定替代、自相矛盾）→ DEFERRED，按 `docs/agents/issue-tracker.md` 写票，文档和代码都不动（自相矛盾且影响主流程的属硬阻塞）。
- **就地修复**：改动局限在一个模块内，不改数据 schema、公共接口或配置键，不涉及设计取舍。任一条不满足 → DEFERRED 写票，继续下一项。
- **硬阻塞**：见下文。

就地修复的流程：

1. 按项目测试分层约定（有 `docs/agents/testing.md` 时依其归入 core 或 full）补一个重现缺陷的失败测试；纯界面表现类可免，账本注明理由。
2. 修复，运行相关测试与 `mise run gate-core`（有则跑，失败如实记录）。
3. 一处修复一个 commit 到当前分支，message 引用验收项编号。
4. 需要重启时用契约的停止与启动命令；修复涉及数据写入时先重置再重跑。
5. 重跑该项及同一来源文件（同一 behaviors 主题或同一模块页）的全部项；通过后记 FIXED。

**硬阻塞**时停下问用户，附账本路径与当前摘要，用户答复后从账本继续：

- 契约声明的命令不存在或运行失败；服务起不来或就绪超时。
- 缺凭证；所选浏览器方案不可用（CLI 缺失，原生方案未连接、连接断开或缺所需工具）；页面被原生对话框（alert/confirm）阻塞。
- 需要契约未授权的破坏性操作。
- 文档自相矛盾且影响主流程。
- 修复需要 schema 变更或跨模块重构。
- 同一项修复两次仍失败。

## 阶段 5：收敛与报告

1. 所有项都是 PASS、FIXED、DEFERRED 或 `无法观测` 后，若本次有过修复：重置数据（契约有命令时）、重启服务、全量重跑（主题模式只重跑该主题），要求零修复；重跑中又需修复就回阶段 4，之后再来一次。
2. 用契约的停止命令停服务，确认进程与子进程都已退出；按 browser.md 收尾。
3. 按 [templates/report.md](templates/report.md) 写 `docs/research/acceptance/<topic 或 all>-<YYYY-MM-DD>.md`（同日已有则加 `-2`、`-3`），在 `docs/research/INDEX.md` 的“验收记录”表登记一行，单独 commit。
4. 打印最终摘要：结果计数、修复 commit 列表、票据列表、报告路径；报告 commit 之后，末行单独打印 `验收完成`。

## 边界

- 预期以文档为准：不改文档迁就代码、不弱化预期、不跳过项；未覆盖与无法观测如实进报告。
- 与验收项无关的缺陷只写票。
- 只在当前分支本地 commit：不 push、不开 PR、不切换分支、不改写历史。
- 契约禁区一概不碰。
