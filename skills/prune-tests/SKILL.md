# 精简测试

对调用时当前工作目录的项目生效。目标是大幅减少测试数量、维护成本和执行时间：默认删除非核心测试，不追求覆盖率。产品行为合同不随测试删减而改变，门禁通过只证明保留范围。

## 约定来源

动手前按顺序读取：

1. 分层合同：`docs/agents/testing.md` 的分层规则，以及 `docs/development/test-layers.md` 整页（各层目录、收录入口、独占资源与串行约束，以及上次精简的保留范围）。分层合同只认这个路径。
2. 命令契约：`mise.toml` 与 `mise-tasks/` 中的 `test`、`test-full`、`gate-core`、`gate-full` 各覆盖什么。
3. 主流程来源：`docs/behaviors/*.md`，其次 `docs/architecture/modules/*.md` 的“当前行为规格”章节。
4. 核心规则来源：模块页“当前行为规格”里的不变量与状态转换、`GLOSSARY.md`、模块边界文档。

项目约定决定分层结构（目录、收录入口、资源边界、串行约束）；保留标准以本 skill 为准，项目文档里“穷举规则表”“全覆盖”之类的要求按[文档同步](#文档同步)改写。没有这些文档时用[通用标准](#通用标准无分层约定时)，从产品入口、架构和实现推断核心规则与主流程，并在报告注明“依据代码推断”。

## 按层保留标准

### core：`gate-core` 收录，必须可并发

- 只留核心业务规则与核心算法的代表性单元测试，经公开接口验证，足以发现主要逻辑错误即可。
- 同一套 core 会在多个 worktree 同时运行：只用测试自己申请的临时目录和进程内替身，不占固定端口、共享数据库、固定路径或用户目录，不依赖桌面焦点与共享浏览器 profile，不启动真实服务，不执行 E2E，秒级完成。
- 各 stack 的工具链自检测试（Python 版本符合 `.python-version`、Node 版本符合 `mise.toml`、Xcode 版本符合 `.xcode-version` 等）一律保留：它们保证 core 不会零收集。

### full：`gate-full` 收录，主机锁内串行

保留两类：

- `docs/behaviors/` 每个主题“操作与可观察结果”节的主路径：每条一个（或一组）端到端或集成测试，断言该节写明的可观察结果。没有 `docs/behaviors/` 时取模块页“当前行为规格”的用户可见部分；两处都没有时按通用标准。
- 只有真实接线才能证明的核心规则，如数据库事务合同、真实子进程 smoke。testing.md 禁止为进 core 而 mock 掉待验证边界，所以它们留在 full，报告中逐条给理由。

behaviors 的“边界与错误情况”节默认删除，只有该错误处理本身是产品核心用途（如失败后保留旧文件）才留最小一条。behaviors 主题在 full 中零覆盖时不补测试，列入报告的“未覆盖主题”。

### 通用标准（无分层约定时）

- 核心单元测试：关键业务规则或核心算法的代表性用例。
- 主流程集成测试：用户主要任务经实际模块协作完成，并检查关键结果。
- 已有端到端或界面测试仅在承担主流程验证、且没有等效覆盖时保留。

## 删除标准

大胆删除：

- 边界值、异常输入、罕见失败、故障注入及各种极端情况。
- 并发竞争、复杂时序、压力、极限容量及其组合矩阵。
- 重复验证同一规则的参数化变体和跨层重复：core 已验证的规则不在 full 重复断言，full 已验证的主流程不在 core 用替身再复刻。
- 与实现细节耦合的私有方法、内部调用顺序、机械快照及琐碎断言。
- 历史兼容、过时行为及已失去产品意义的回归测试。
- 测试基础设施的自测：文档检查器、诊断输出、fixture 与替身自身的测试。

测试涉及异常、并发或历史缺陷，本身不是保留理由；只有相关行为属于产品核心用途时才留最小代表性验证。

## 归属校正

只对保留下来的测试做，不扩大为重构：

- core 里启动真实服务、占端口、读写共享目录或依赖桌面的测试：属于 full 主流程就迁到 full，否则删除。判断看 fixture、子进程和输出路径的实际副作用，不以“当前恰好没冲突”为准。
- full 里不碰任何真实资源的纯逻辑测试迁回 core；E2E 与真实集成即使很快、已隔离也留在 full。
- 迁移只改位置和收录，不改替身：不为进 core 把数据库、子进程或网络换成 mock。
- conftest、helper 与测试数据随迁移拆分；core 的公共 fixture 不得隐含启动服务或占用共享资源。

## 执行方式

1. 读取约定来源，列出核心规则清单与主流程清单，每条标注来源文件。
2. 记录基线：各层测试文件数与用例数；条件允许时运行无筛选的 `mise run gate-full`（或项目等价入口），记录结果与耗时，gate-core 耗时从其输出或单独计时取，已有失败如实记录。
3. 逐个读测试正文下去留结论：每条结论写明该测试断言的可观察结果，以及对应的核心规则或主流程来源；只有名称没有断言的结论不算完成。委派分析时把这一条作为子 agent 的交付标准。
4. 按层删除与校正归属，压缩重复矩阵：
   - 按内容定位编辑（Edit 工具或匹配断言内容的脚本），不按行号范围删除。
   - 删除后由 typecheck 与 lint 报出失去引用的 helper、导入和变量，逐个删除其声明；只剩一组参数的参数化测试改写为普通测试；清理失去引用的数据和夹具。
   - full 目录删空后删除目录本身：只剩空目录或非测试文件时 `gate-full` 按契约提示通过，残留测试文件却零收集会失败。
   - 保留测试的关键行为与结果断言原样保留。
5. 验证：先用 runner 的收集命令（如 `pytest --collect-only`、`vitest list`）确认保留与迁移的测试仍被标准入口发现，再由发起本 skill 的 agent 运行无筛选的 `mise run gate-full`（没有 mise task 契约时用项目的完整测试入口）。full 经主机锁排队，等待不是失败。
6. 按下节同步文档。
7. 留痕：按 `docs/agents/issue-tracker.md` 建一张票，拿到票据编号后再单独关闭；正文记各层清理前后的文件数与用例数，以及写入 `test-layers.md` 的保留范围。本次由某张票据发起时记入那张票，不另建；项目没有 tracker 约定时跳过并在报告注明。

测试要真正删除；skip、禁用目录、调整筛选条件、删断言、全量 mock、降低覆盖率门槛或取消检查都不算完成。只调整清理直接涉及的测试配置，不改产品实现，不补回被删的边缘测试；去留按保留标准判断，不按能否让检查变绿判断。清理带出的引用、导入和夹具问题就地修复；发现产品缺陷时单独报告，不在本次修。

## 文档同步

- `docs/development/test-layers.md` 的保留范围部分：写入本次之后的保留范围（core 聚焦哪些规则，full 覆盖哪些主流程与接线合同，明确不再维护的测试类别），末尾保留一句“产品行为合同不随测试删减而改变，完整门禁通过仅证明上述保留范围”；仍是 `<待填` 标记就替换。分层合同部分不动。文件不存在就新建：页头照 `docs/development/` 下其他页面的写法（含元数据块），从 `docs/agents/testing.md` 加一句链接指向本页，并登记到 development 索引（没有目录索引时登记到 `docs/INDEX.md`）。
- 模块页“代码与验证入口”：移除指向已删测试的引用，被删掉的覆盖写进该节的已知限制与未验证范围说明。
- `docs/agents/testing.md`、模块边界等文档里项目专属的分层标准、独占资源清单和覆盖要求，与精简后的事实保持一致。
- 其他引用了被删测试或目录的说明与执行入口随之更新；有文档检查命令（如 `mise run docs-check`）时运行它。

## 完成报告

- 核心规则清单与主流程清单，及各自来源（behaviors、模块页或代码推断）。
- 按层的删除类别与数量变化：core、full 各自文件数与用例数的前后对比；迁移的测试列表。
- full 中保留的非 behaviors 测试及理由；behaviors 的未覆盖主题。
- 实际运行的检查与结果（收集验证、`gate-full`）；未运行、零匹配或失败的项照实列出，不算通过。
- 有可比实测时各层耗时前后对比，注明环境或缓存差异；gate-core 是否仍在秒级。
- 删后 `gate-full` 按文件的耗时分布，指出占大头的固定开销（如每个文件各启动一次服务或容器、写死的等待），列为后续优化项，本次不改。
- 已更新的文档；留痕票据编号，或未建的原因。
