# 精简测试

本 skill 安装在用户级，对调用时当前工作目录的项目生效。目标是大幅减少测试数量、维护成本和执行时间：默认删除非核心测试，不追求覆盖率，不因“可能有用”保留边缘场景。产品行为合同不随测试删减而改变，门禁通过只证明保留范围。

## 约定来源

动手前按顺序读取：

1. 分层合同：`docs/agents/testing.md` 的分层节，以及 `docs/development/workflow.md` 的“测试分层与资源边界”节：各层目录、收录入口、独占资源清单与串行约束。
2. 命令契约：`justfile` 是否有 `test`、`test-full`、`gate-core`、`gate-full`，各自覆盖什么。
3. 主流程来源：`docs/behaviors/*.md`，其次 `docs/architecture/modules/*.md` 的“当前行为规格”章节。
4. 核心规则来源：模块页“当前行为规格”里的不变量与状态转换、`GLOSSARY.md`、模块边界文档。

项目约定决定分层结构：各层目录、收录入口、资源边界与串行约束。保留标准以本 skill 为准；项目文档里要求穷举规则表或全覆盖的表述，按[文档同步](#文档同步)改写。

没有这些文档的项目退回[通用标准](#通用标准无分层约定时)：从产品入口、架构和实现识别核心规则与主流程，并在报告注明“依据代码推断”。

## 按层保留标准

项目有 core/full 分层（setup-project 初始化的项目默认有）时按层判断。

### core：`gate-core` 收录，必须可并发

- 只保留核心业务规则与核心算法的代表性单元测试，经公开接口验证，足以发现主要逻辑错误即可。
- 硬性资源要求：同一套 core 测试会在多个 worktree 同时运行，彼此不得干扰。不占固定端口、共享数据库、固定路径或用户目录，不依赖桌面焦点与共享浏览器 profile，不启动真实服务，不执行 E2E，秒级完成。每个测试只用自己申请的临时目录和进程内替身。
- 各 stack 自带的工具链自检测试（Python 版本符合 `.python-version`、Bun 版本符合 `mise.toml`、Xcode 版本符合 `.xcode-version` 之类）不删：它保证 core 不会零收集。

### full：`gate-full` 收录，主机锁内串行

- 保留两类。一是 `docs/behaviors/` 每个主题“操作与可观察结果”节的主路径：每条主路径一个（或一组）端到端或集成测试，断言该节写明的可观察结果。二是只有真实接线才能证明的核心规则，如数据库事务合同、真实子进程 smoke：它们不是 behaviors 主流程，但 testing.md 禁止为了进 core 而 mock 掉待验证边界，所以留在 full，报告中逐条给出理由。
- behaviors 的“边界与错误情况”节默认删除；只有该错误处理本身是产品核心用途（如失败后保留旧文件）才留最小一条。
- behaviors 主题在 full 中零覆盖时不补测试，列入报告的“未覆盖主题”。
- 没有 `docs/behaviors/` 时，主流程取模块页“当前行为规格”的用户可见部分；两处都没有时按通用标准处理。

### 通用标准（无分层约定时）

- 核心单元测试：验证关键业务规则或核心算法，只保留足以发现主要逻辑错误的代表性用例。
- 主流程集成测试：验证用户主要任务通过实际模块协作完成，并检查关键结果。
- 已有端到端测试或界面测试仅在承担主流程验证、且没有等效覆盖时保留。

## 删除标准

大胆删除以下测试：

- 边界值、异常输入、罕见失败、故障注入及各种极端情况。
- 并发竞争、复杂时序、压力、极限容量及其组合矩阵。
- 重复验证同一规则的参数化变体和跨层重复：core 已验证的规则不在 full 重复断言，full 已验证的主流程不在 core 用替身再复刻一遍。
- 与实现细节耦合的私有方法、内部调用顺序、机械快照及琐碎断言。
- 历史兼容、过时行为以及已经失去实际产品意义的回归测试。
- 测试基础设施的自测：文档检查器、诊断输出、fixture 与替身自身的测试。

不要因为测试涉及异常、并发或历史缺陷就自动认定它重要。只有当相关行为本身属于产品的核心用途时，才保留最小代表性验证；其余边缘变体仍然删除。

## 归属校正

只对保留下来的测试做，顺手完成，不扩大为重构：

- core 里启动真实服务、占端口、读写共享目录或依赖桌面的测试：属于 full 主流程就迁到 full 目录，否则删除。判断看 fixture、子进程和输出路径的实际副作用，不以“当前恰好没冲突”为准。
- full 里不碰任何真实资源的纯逻辑测试迁回 core。“即使已隔离也按验证范围归入”：E2E 与真实集成即使很快也留在 full。
- 迁移只改位置和收录，不改替身：不为进入 core 把数据库、子进程或网络换成 mock。
- 迁移后 conftest、helper 与测试数据随之拆分；core 的公共 fixture 不得隐含启动服务或占用共享资源。

## 执行方式

1. 读取约定来源，列出核心规则清单与主流程清单，每条标注来源文件。
2. 记录清理前规模：各层测试文件数与用例数。条件允许时运行无筛选的 `just gate-full`（或项目等价入口）记录基线结果与耗时，gate-core 耗时从其输出或单独计时取，已有失败如实记录。
3. 逐个读测试正文做去留结论：每条结论写明该测试断言的可观察结果，以及它对应的核心规则或主流程来源；只有名称没有断言的结论不算完成。委派分析时把这一条作为子 agent 的交付标准。
4. 按层执行删除与归属校正，压缩重复矩阵，清理失去引用的辅助代码、数据和夹具。编辑用按内容定位的方式（Edit 工具或匹配断言内容的脚本），不用行号范围删除。full 目录删空后删除目录本身：只剩空目录或非测试文件时按契约提示通过，残留测试文件却零收集会让 `gate-full` 失败。
5. 保留测试中的关键行为与结果断言；不得通过删断言、全量 mock 或跳过执行制造通过。
6. 验证收录与门禁：先用 runner 的收集命令（如 `pytest --collect-only`、`bun test --dry-run` 或等价手段）确认保留与迁移的测试仍被标准入口发现，再由发起本 skill 的 agent 运行无筛选的 `just gate-full`。full 经主机锁排队，等待不是失败。没有 just 契约时运行项目的完整测试入口。
7. 按下节同步文档。

真正删除测试，不通过 skip、禁用测试目录或调整筛选条件隐藏测试。只调整清理直接涉及的测试配置，不降低覆盖率门槛或取消检查来绕过失败。默认不修改产品实现，也不顺手补回被删除的边缘测试。测试去留以保留标准判断，不以能否让检查变绿判断。清理导致的引用、导入和夹具问题应修复；发现产品缺陷时单独报告，不在本次修。

## 文档同步

- `docs/development/workflow.md` 的 `## 回归覆盖与保留范围`：写入（或改写）本次之后的保留范围：core 聚焦哪些规则，full 覆盖哪些主流程与接线合同，明确不再维护的测试类别；末尾保留一句“产品行为合同不随测试删减而改变，完整门禁通过仅证明上述保留范围”。节不存在就新建，仍是 `<待填` 标记就替换。
- 模块页“代码与验证入口”：移除指向已删测试的引用，被删掉的覆盖写进该节的已知限制与未验证范围说明（模块页没有独立标题，它是该节的内容项）。
- `docs/agents/testing.md`、模块边界等文档里项目专属的分层标准、独占资源清单，以及“穷举规则表”之类的覆盖要求，与精简后的事实保持一致。
- 其他引用了被删测试或目录的说明与执行入口随之更新。有文档检查命令（如 `just docs-check`）时运行它。

## 完成报告

简要说明：

- 核心规则清单与主流程清单，以及各自来源（behaviors、模块页或代码推断）。
- 按层给出删除的主要类别与数量变化：core、full 各自的文件数与用例数前后对比；迁移的测试列表。
- full 中保留的非 behaviors 测试及理由；behaviors 的未覆盖主题。
- 实际运行的检查与结果：收集验证、`gate-full`；未运行或失败的项。
- 有可比实测时各层耗时前后对比，注明环境或缓存差异；gate-core 是否仍在秒级。
- 已更新的文档。

未运行、零匹配或失败不能算通过。不自动提交或推送。
